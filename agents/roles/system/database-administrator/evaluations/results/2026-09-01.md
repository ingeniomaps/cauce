### 1 — No hay «base por defecto» que borrar. Verificado

Una variable vacía **sin comillas** no deja un argumento vacío: desaparece en la división de palabras y quedan **cero argumentos**. Y `dropdb` sin argumento posicional no elige nada por defecto, falla antes de abrir una conexión:

```
$ EMPTY=""; dropdb -h /nonexistent -w $EMPTY
dropdb: error: missing required argument database name
dropdb: hint: Try "dropdb --help" for more information.
EXIT=1
```

Que el fallo es anterior a la conexión no lo supongo: la variante que **sí** llega a conectarse falla con otro mensaje contra ese mismo host inexistente (`connection to server on socket ... failed`). Concuerda con `man dropdb` 16.15, donde `dbname` va fuera de corchetes: `dropdb [connection-option...] [option...] dbname`.

**Consecuencia para el postmortem:** si una base desapareció, la llamada que la borró **le pasó un nombre**. Encontrar cuál es el trabajo que esta lección, publicada como está, cancelaría — la causa quedaría dada por cerrada y apuntando al lugar equivocado.

### 2 — No pide confirmación. Cierto, y es opt-in explícito

> `-i`, `--interactive` — Issues a verification prompt before doing anything destructive. (`man dropdb`, 16.15)

Es cierto y no sostiene el punto 1: no hay confirmación **cuando la invocación es válida**, y la descrita no lo es.

### 3 — No imprime el nombre. Documentado, con un matiz que hay que decir

El eco de la sentencia también es opt-in (`-e`/`--echo`). El camino de éxito no lo verifiqué: exigiría conectarse a un servidor real y ejecutar la operación cuyo efecto se describe. Queda **documentado**, no verificado.

El matiz: **con `-i` el nombre sí se imprime**, en el propio prompt. Verificado:

```
$ echo n | dropdb -h /nonexistent -w -i -e pagos_prod
Are you sure? (y/n) Database "pagos_prod" will be permanently removed.
```

Una lección que diga «no imprime el nombre» sin ese matiz enseña a descartar la única opción que sí sirve.

### 4 — `IF EXISTS` no evita nada, y en un caso empeora

> `IF EXISTS` — Do not throw an error if the database does not exist. A notice is issued in this case.
> (`man 7 DROP_DATABASE`, 16.15; frase idéntica para `--if-exists` en `man dropdb`)

No cambia **qué** base se elige, ni agrega confirmación, ni agrega eco. Comprobado sobre las dos formas: con `--if-exists` el resultado es byte por byte el mismo, tanto con cero argumentos (`missing required argument database name`, exit 1) como con el argumento vacío (mismo error de conexión, exit 1).

Y en el escenario que sí importa —la variable trae un nombre **equivocado**— la cláusula empeora el caso:

- **El nombre equivocado no existe:** sin la cláusula, falla y el script se detiene con la pista de que el nombre estaba mal. Con la cláusula, emite un aviso y **termina con éxito**: convierte «no borré nada» en «listo».
- **El nombre equivocado existe:** la borra igual, con cláusula o sin ella. La cláusula no mira *qué* base es, sólo si está.

Éste es el único punto que considero bloqueante para publicar.

## Las cuatro formas, para que el postmortem elija la correcta

| Forma | Tras la división de palabras | Resultado observado (16.15) |
|---|---|---|
| `dropdb $DB` con `DB=""` | cero argumentos | `missing required argument database name`, exit 1, sin conexión |
| `dropdb "$DB"` con `DB=""` | un argumento vacío | pasa el análisis y **llega a conectarse** |
| `dropdb $DB` con `DB="mi base"` | dos argumentos | `too many command-line arguments (first is "base")`, exit 1 |
| `dropdb $DB` con `DB="pagos_prod"` | un argumento | conecta y borra lo que el nombre diga |

## Lo que sí frena esta falla — verificado sobre bash 5.2.21(1)

La salvaguarda que probablemente quieran es del shell, no del motor, y tiene una trampa que va en la misma línea:

```
$ bash -c 'set -u; unset DB; echo "[$DB]"'                    → exit 127  (atrapa la NO DEFINIDA)
$ bash -c 'set -u; DB=""; set -- $DB; echo $#'                → exit 0, "0"  (NO atrapa la vacía)
$ bash -c 'DB=""; echo "${DB:?falta el nombre}"'              → exit 127  (sí atrapa la vacía)
$ bash -c 'DB=""; echo "[${DB?no definida}]"'                 → exit 0, "[]"  (los dos puntos importan)
```

**`set -u` no atrapa una variable definida y vacía**, que es exactamente el caso del incidente. Un postmortem que recomiende `set -u` y nada más deja la falla en pie y nadie lo nota hasta la próxima vez.

Ordenado por cuánto cubre: `: "${DB:?falta el nombre de la base}"` (ataca la causa) · entrecomillar `"$DB"` · `-i` en lo interactivo · `-e` en lo desatendido, que deja en el log la sentencia exacta —la evidencia que a este postmortem le falta— · y **no** `--if-exists` en el borrado deliberado.

Las cinco son propuestas de procedimiento. Ninguna se ejecutó sobre ningún sistema.
