## Hallazgos

**H1 — PostgreSQL publicó el 2026-08-13 un release de seguridad que corrige cinco CVE en todas las
ramas soportadas (14 a 18).** Tres son de severidad alta (CVSS 8.8), una media (4.3) y una baja (3.8).
Versiones corregidas: 18.6, 17.11, 16.15, 15.19 y 14.24 (también 19 Beta 3 para las tres de severidad
alta). **Registro: verificado**, contra las páginas de cada CVE (ver Evidencia).

**H2 — La rama 14, una de las cinco alcanzadas por H1, sale de soporte el 2026-11-12** — poco más de
dos meses desde la fecha de este informe —, según la política de versionado oficial. Es la única de
las cinco ramas parchadas que no llega a la próxima ventana trimestral de parches como versión
soportada. **Registro: documentado** (política de versionado, no comprobado contra un binario local).

**H3 — Dos de los tres CVE de severidad alta habilitan ejecución de código a través del ciclo
backup/restore, no de una conexión de red directa.** `CVE-2026-19385` (pg_dump, buffer overflow en
listas de transform) y `CVE-2026-18408` (psql `\unrestrict`) requieren que quien genera el dump — o el
propio motor origen — sea la fuente del vector; `CVE-2026-18408` además documenta que el fix de un CVE
previo (`CVE-2025-8714`, que introdujo `\restrict`/`\unrestrict`) quedó incompleto: `\unrestrict` solo
ya alcanzaba para el ataque. **Registro: verificado**, cita literal en Evidencia.

**H4 — PostgreSQL 19 Beta 3 se publicó el mismo 2026-08-13.** No es material de aplicación productiva,
pero es la primera beta de la próxima rama mayor y abre ventana para pruebas de compatibilidad antes
de un GA. **Registro: documentado** (nota de la página de release notes, sin verificación adicional).

## Evidencia

**H1**, cita literal de `CVE-2026-19385`:

> Heap buffer overflow in PostgreSQL pg_dump of long function transform lists allows an object creator
> to execute arbitrary code as the operating system user running pg_dump, via a crafted transform
> list. […] CVSS 3.0: 8.8 — AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H. Affected: 18 (before 18.6), 17
> (before 17.11), 16 (before 16.15), 15 (before 15.19), 14 (before 14.24). Fixed: 18.6, 17.11, 16.15,
> 15.19, 14.24, 19 Beta 3.

y de `CVE-2026-16239` (tipo confusión en ciclo de vida de cursor/portal, CVSS 8.8,
AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H, mismas versiones afectadas y corregidas que arriba); de
`CVE-2026-18024` (buffer over-read en `ascii()`, CVSS 4.3, hasta 3 bytes de una asignación adyacente);
de `CVE-2026-16241` (integer underflow en ECPG, CVSS 3.8, denegación de servicio del lado cliente).

**H2**, tabla de la política de versionado (`postgresql.org/support/versioning`):

> 14 | 14.24 | September 30, 2021 | November 12, 2026

**H3**, cita literal de `CVE-2026-18408`:

> Untrusted data inclusion in pg_dump in PostgreSQL allows a malicious superuser of the origin server
> to inject arbitrary code for restore-time execution as the client operating system account running
> psql to restore the dump, via psql `\restrict` meta-command input expansion. The fix for
> CVE-2025-8714 introduced `\restrict` and `\unrestrict` to block this attack, but `\unrestrict` itself
> was sufficient for an attack. pg_dumpall is also affected. pg_restore is affected when used to
> generate a plain-format dump.

**H4**, título de la entrada más reciente en `postgresql.org/docs/release/`: «PostgreSQL 18.6, 17.11,
16.15, 15.19, 14.24, and 19 Beta 3 Released», fechada 2026-08-13.

## Posibles prácticas obsoletas

- Operar cualquier instancia en 18.x, 17.x, 16.x, 15.x o 14.x por debajo de 18.6/17.11/16.15/15.19/14.24
  respectivamente, dado H1: las tres vulnerabilidades de severidad alta permiten ejecución de código.
- Tratar un dump generado por un superusuario del origen, o el propio archivo de dump, como insumo
  confiable por defecto para `pg_restore`/`psql` sin revisar su procedencia — H3 muestra que el
  mecanismo de contención introducido para esto (`\restrict`/`\unrestrict`) tuvo una brecha propia hasta
  el parche del 2026-08-13.
- Postergar la migración fuera de la rama 14 más allá de 2026-11-12 (H2) sin una decisión explícita que
  lo sostenga.

## Recomendación

Sobre H1 y H3: priorizar, para todo motor PostgreSQL bajo administración, la actualización menor a
18.6/17.11/16.15/15.19/14.24 siguiendo el flujo de cambio propio del cargo (ventana, prechecks,
verificación de versión antes y después, plan de rollback) — la política de versionado documenta que
una actualización menor no exige dump/restore, sólo reemplazar binarios y reiniciar, pero eso no
exime del resto del procedimiento de cambio. Mientras no esté aplicado el parche, tratar cualquier
restore desde un dump de origen no auditado como de mayor riesgo (H3).

Sobre H2: confirmar si existe already un plan de migración fuera de la rama 14 para las instancias que
la usen, con fecha anterior a 2026-11-12; si no existe, es una decisión para quien tenga la autoridad
sobre esas instancias, no para este ciclo de aprendizaje.
