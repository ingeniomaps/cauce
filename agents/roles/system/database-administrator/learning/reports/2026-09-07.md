## Hallazgos

**H1 — El release del 2026-08-13 (18.6/17.11/16.15/15.19/14.24) corrige 28 vulnerabilidades de
seguridad, no cinco.** El informe del 2026-08-31 registró cinco CVE para ese release (H1 de esa
semana), tomados de una lectura parcial de la tabla histórica de `postgresql.org/support/security/`.
El anuncio oficial del release enumera 28 CVE distintos, catorce de ellos con CVSS 8.8. El subconteo no
afecta la recomendación de esa semana —parchar sigue siendo la acción—, pero sí su magnitud: la
superficie de ejecución de código remoto corregida es casi tres veces mayor a la registrada.
**Registro: verificado**, cita literal en Evidencia.

**H2 — Una de las 28, `CVE-2026-6471`, es una falla de autorización en logical decoding presente desde
PostgreSQL 9.4 (2014): doce años.** Una cuenta sin privilegio de superusuario que tenga el atributo
`REPLICATION` puede elegir el plugin de salida de un slot de replicación lógica y hacer que el servidor
cargue (`dlopen`) cualquier archivo visible al proceso — código arbitrario ejecutado como el usuario de
sistema operativo del servidor. CVSS 7.2 (`PR:H` porque exige el atributo `REPLICATION`, no
superusuario). **Registro: verificado**, cita literal del aviso oficial en Evidencia.

**H3 — El fix de H2 introduce un parámetro nuevo, `output_plugin_libraries`, con default que sólo
permite los plugins que trae PostgreSQL (`pgoutput`, `test_decoding`).** Toda instalación que use un
plugin de logical decoding de terceros necesita agregarlo a esa lista después de actualizar, o
`pg_upgrade --check` falla al migrar desde 17 en adelante si el clúster de origen tiene slots con un
plugin no incluido en la lista del clúster nuevo. **Registro: verificado**, cita literal del changelog
oficial en Evidencia.

**H4 — ISO/IEC 27040 está en su segunda edición, 2024, no en la de 2015 citada en `sources.yaml`.**
La petición directa a `iso.org/standard/80194.html` volvió a devolver HTTP 403, igual que la semana
pasada, pero el título indexado de esa misma URL en resultados de búsqueda dice «ISO/IEC 27040:2024 —
Information technology — Security techniques — Storage security», y coincide con lo que reportan
`webstore.iec.ch` e `iso27001security.com` para la misma norma. ISO 22301, en cambio, sigue en su
edición de 2019: el título indexado de `iso.org/standard/75106.html` no cambió. **Registro:
documentado** (título de la página oficial vía resultado de búsqueda, no la página misma — sigue sin
poder abrirse directamente; ver Preguntas abiertas).

## Evidencia

**H1**, cita literal del anuncio oficial (`postgresql.org/about/news/...-3365/`):

> This release fixes 28 security vulnerabilities and over 110 bugs reported over the last several
> months.

Del listado de esa misma página, los CVE con CVSS 8.8 son: `CVE-2026-14662`, `CVE-2026-14664`,
`CVE-2026-14669`, `CVE-2026-14670`, `CVE-2026-14671`, `CVE-2026-14676`, `CVE-2026-14677`,
`CVE-2026-14680`, `CVE-2026-15741`, `CVE-2026-15742`, `CVE-2026-16238`, `CVE-2026-16239`,
`CVE-2026-18408` y `CVE-2026-19385` — catorce en total, sobre los tres que el informe anterior había
registrado en esa banda.

**H2**, cita literal de `CVE-2026-6471`:

> Missing authorization in PostgreSQL logical decoding allows a non-superuser holding REPLICATION
> privilege to dlopen any file visible to the operating system account running the server, via the
> choice of logical decoding plugin. This in turn runs arbitrary code as that account. […] CVSS 3.0:
> 7.2 — AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H. Affected: 18 (before 18.6), 17 (before 17.11), 16 (before
> 16.15), 15 (before 15.19), 14 (before 14.24).

The Hacker News (fuente secundaria, no verificada independientemente por este informe contra el código
fuente) atribuye a «Cyera Research» la lectura de que `REPLICATION` funciona en la práctica como
credencial de bajo privilegio porque la sostienen herramientas de backup, standbys, pipelines de CDC y
monitoreo, y describe como ruta de explotación la resolución de rutas de red (SMB en Windows,
automontaje NFS en Linux/macOS) para obtener una librería maliciosa. **Registro: documentado**, no
verificado por este informe.

**H3**, cita literal del changelog de `release-18-6.html`:

> Restrict logical decoding output plugins to the set specified by a new server parameter
> `output_plugin_libraries` (Jacob Champion) — Previously, a replication user could select any
> loadable library for logical decoding, allowing exploits of various sorts. […] By default, only the
> output plugins shipped as part of PostgreSQL (pgoutput and test_decoding) are included in
> `output_plugin_libraries`. […] Additionally, pg_upgrade --check will fail if the
> output_plugin_libraries parameter on the new cluster does not permit the plugins of logical
> replication slots on the old cluster, when migrating from versions 17 and later.

**H4**, títulos indexados: «ISO/IEC 27040:2024 - Information technology — Security techniques — Storage
security» para `iso.org/standard/80194.html`; «ISO 22301:2019 - Business continuity management systems»
para `iso.org/standard/75106.html`. Ninguna de las dos páginas se pudo abrir directamente esta corrida
(HTTP 403 en ambas).

## Posibles prácticas obsoletas

- Citar «cinco vulnerabilidades» para el release 2026-08-13 al comunicar la urgencia de un parche
  (H1): subestima en casi 5x la superficie de RCE corregida y puede haber bajado la prioridad asignada
  la semana pasada.
- Actualizar a 18.6/17.11/16.15/15.19/14.24 sin revisar antes qué plugins de logical decoding usa cada
  slot existente (H3): con el default de `output_plugin_libraries`, cualquier plugin que no sea
  `pgoutput` o `test_decoding` deja de estar permitido y `pg_upgrade --check` corta la migración —o, si
  el camino de actualización no pasa por `pg_upgrade --check` (una actualización menor in-place),
  el slot que dependía de ese plugin puede quedar inutilizable después del reinicio.
- Tratar el atributo `REPLICATION` como un privilegio de bajo riesgo por default al aprovisionar cuentas
  de backup, standbys o pipelines de CDC (H2): antes del parche, ese atributo alcanzaba para ejecución
  de código como el usuario de sistema operativo del servidor.
- Dar por buena la lista de fuentes de `sources.yaml` sin revisar su edición: la entrada de ISO/IEC
  27040 apunta a la norma vigente pero el catálogo interno no distingue que es la edición 2024 (H4).

## Recomendación

Sobre H1: si la actualización a 18.6/17.11/16.15/15.19/14.24 (recomendada la semana pasada) todavía no
se aplicó, tratarla con la urgencia de 28 CVE corregidos —catorce de severidad alta con ejecución de
código—, no de cinco.

Sobre H2 y H3: antes de aplicar esa actualización en cualquier instancia con logical decoding activo,
inventariar los plugins de salida en uso por cada slot (`pg_replication_slots.plugin`) y, si alguno no
es `pgoutput` ni `test_decoding`, agregarlo a `output_plugin_libraries` en la configuración del clúster
de destino antes del cambio — siguiendo igual el flujo propio del cargo (ventana, prechecks, plan de
rollback). Revisar además qué cuentas tienen el atributo `REPLICATION` y si cada una lo necesita,
dado que H2 mostró un camino real de esa cuenta a ejecución de código como superusuario del sistema
operativo.

Sobre H4: no hay cambio de procedimiento que proponer — es una corrección de metadato. Si se
actualiza `sources.yaml`, fijar la edición 2024 en la entrada de ISO/IEC 27040 evita que una lectura
futura asuma la edición 2015 por default.

## Preguntas abiertas

- Edición vigente exacta de ISO/IEC 27040 y de ISO 22301, confirmada abriendo la página misma: las dos
  siguen devolviendo HTTP 403 a la petición directa por segunda semana consecutiva; H4 se apoya en el
  título indexado por el buscador sobre la misma URL, no en el documento. No se probó una vía
  alternativa de acceso (compra, espejo de la norma, buscador distinto).
- Si existe una revisión posterior a NIST SP 800-34 Rev. 1 Update 1: una búsqueda dirigida esta semana
  («NIST SP 800-34 revision 2 2026») no devolvió ninguna mención de una Rev. 2, lo mismo que la lectura
  directa de la página de CSRC. Sigue sin recorrerse el listado completo de publicaciones de NIST CSRC,
  así que la ausencia queda documentada, no verificada exhaustivamente.
- Si alguna instancia real bajo este cargo usa logical decoding con un plugin de salida distinto de
  `pgoutput`/`test_decoding`, y si alguna cuenta con `REPLICATION` es más amplia de lo necesario (H2,
  H3): este informe es investigación de fuente pública, no inventario de una instancia — le corresponde
  a quien administre cada motor concreto.
- Si el camino de actualización menor in-place (sin `pg_upgrade`) también revisa `output_plugin_libraries`
  contra los slots existentes o sólo lo hace `pg_upgrade --check`: el changelog citado en H3 sólo
  documenta el comportamiento de `pg_upgrade --check` desde la versión 17; no se verificó el
  comportamiento de un reinicio in-place sobre una instalación con slots preexistentes.
