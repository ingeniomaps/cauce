### Qué pasa realmente

1. `DB=""` **sin comillas**: el word splitting borra la palabra. Verificado: `set -- $DB; echo $#` → `0`; con comillas → `1`, `arg1=[]`.
2. Cero posicionales → `dropdb` **aborta antes de conectarse**, exit 1.
3. **Con** comillas la cadena vacía sí cuenta como argumento —verificado con `dropdb "" ""` → `too many command-line arguments (first is "")`—, así que `dropdb "$DB"` conecta y envía `DROP DATABASE ""`. Que el servidor lo rechace por identificador de longitud cero es **hipótesis**: comprobarlo exigiría conectarme a un servidor real.
4. **De dónde sale la creencia**: del mismo paquete. `createdb` declara `[DBNAME]` opcional y «The default is to create a database with the same name as the current system user». `dropdb` no tiene ese default —su ENVIRONMENT lista `PGHOST`, `PGPORT`, `PGUSER` y **no** `PGDATABASE`—. Crear defaultea al usuario; borrar no.

### Por qué `IF EXISTS` es el peor control posible acá

Responde a «¿y si no existe?», no a «¿y si es la que no era?». Sobre la base equivocada que sí existe, la borra igual y sin ruido. Sobre el nombre vacío, **elimina el error**: el caso «no existe» sale por notice con exit 0 y el job que reventaba queda verde. El control propuesto no previene el borrado y apaga la única alarma que quedaba.

### Lo operativamente importante

Si en el incidente **desapareció una base de verdad**, este mecanismo no la borró: esa ruta aborta con exit 1. Quedan dos posibilidades y las dos son peores que el postmortem propuesto — **la causa raíz sigue viva** (la variable no estaba vacía sino equivocada, o el comando fue otro, o el clúster fue otro), o **el motor no es PostgreSQL** y el análisis correspondía a otra herramienta. Firmar hoy cierra el incidente sobre una causa que no lo explica.

### Controles que sí corresponden

`set -euo pipefail` y `${DB:?}` (documentado, no verificado acá) · comillas siempre (verificado) · allowlist del entorno antes de invocar · `-i` en toda invocación manual (verificado) · `-e` con salida capturada en lo automatizado (verificado). Aparte, para el runbook: `dropdb --force` termina las conexiones existentes antes de borrar (verificado) — completa lo que hoy fallaría por tener clientes conectados. Si aparece en el script, entra en el análisis.
