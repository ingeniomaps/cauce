## Hallazgos

**H1 — RFC 10008 (junio de 2026) estandariza el método HTTP `QUERY`: seguro, idempotente y con cuerpo de
petición.** [Verificado] Leyendo `rfc-editor.org/rfc/rfc10008.html`: el abstract dice que `QUERY`
«requests that the request target process the enclosed content in a safe and idempotent manner», y el
documento afirma explícitamente «QUERY requests are safe with regard to the target resource», «QUERY
requests are idempotent; they can be retried or repeated when needed» y «the response to a QUERY method
is cacheable». El propio RFC se apoya en RFC 9110 §9.2.1 (safe) y §9.2.2 (idempotent) — la misma fuente
que ya cita `references/operating-model.md`. Es el primer método HTTP nuevo desde `PATCH` (RFC 5789,
2010): llena el hueco entre `GET` (sin cuerpo) y `POST` (sin garantía de idempotencia ni cacheabilidad)
para búsquedas complejas que no entran en una query string.

**H2 — OpenAPI 3.2.0 (19 de septiembre de 2025) ya declara soporte formal para `QUERY`.** [Verificado]
`spec.openapis.org/oas/v3.2.0.html` fecha la versión el 19 de septiembre de 2025 y `oas/latest.html`
confirma que hoy «latest» resuelve a 3.2.0. La nota de release en GitHub
(`OAI/OpenAPI-Specification` tag `3.2.0`) agrega, junto al método `QUERY`, soporte de tipos de medio
secuenciales (`text/event-stream`, `multipart/mixed`) con el campo `itemSchema`, un `mediaTypes`
reusable en `components`, y en seguridad: flujo OAuth2 Device Authorization (`deviceAuthorizationUrl`),
`oauth2MetadataUrl` para metadata del authorization server, y un campo `deprecated` en esquemas de
seguridad.

**H3 — El header `Idempotency-Key` sigue sin ser RFC: el draft de IETF expiró.** [Verificado] La página
del datatracker para `draft-ietf-httpapi-idempotency-key-header` muestra «IESG state: Expired», última
versión -07 con fecha 15 de octubre de 2025, e «Intended RFC status: (None)». El patrón de header
`Idempotency-Key` (popularizado por Stripe y ya recomendado de facto en la industria) no tiene todavía
normalización IETF publicada — a diferencia de `QUERY`, que sí llegó a RFC en el mismo ciclo.

**H4 — OWASP publicó un OWASP Top 10:2025 (proyecto general de aplicaciones web), distinto del OWASP API
Security Top 10 que este cargo sigue.** [Verificado] `owasp.org/Top10/2025/0x00_2025-Introduction/`
confirma que es «the 8th installment of the OWASP Top Ten» (el proyecto general, no el de API) y lista
diez categorías: A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain
Failures (nueva), A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication
Failures, A08 Software or Data Integrity Failures, A09 Security Logging & Alerting Failures, A10
Mishandling of Exceptional Conditions (nueva). SSRF, que en el Top 10 general de 2021 no tenía entrada
propia, sigue sin categoría separada acá; el buscador la reporta absorbida dentro de Broken Access
Control en este proyecto general. **Esto no es el mismo documento que `learning/sources.yaml` rastrea**:
`owasp.org/API-Security/`, leído hoy, sigue mostrando la edición 2023 con sus diez categorías propias
(BOLA, Broken Authentication, Broken Object Property Level Authorization, Unrestricted Resource
Consumption, Broken Function Level Authorization, Unrestricted Access to Sensitive Business Flows, SSRF,
Security Misconfiguration, Improper Inventory Management, Unsafe Consumption of APIs), sin aviso de una
edición 2025/2026 en preparación visible en esa página.

**H5 — OpenTelemetry marcó Stable las convenciones semánticas de spans de cliente de base de datos, con
plan de migración y variable de entorno de opt-in.** [Verificado] `opentelemetry.io/docs/specs/semconv/db/database-spans/`
dice que las convenciones «are Stable (unless otherwise specified for individual attributes)» y exige a
las instrumentaciones existentes que emitían la versión experimental (`v1.24.0` o anterior) introducir
`OTEL_SEMCONV_STABILITY_OPT_IN` con valores `database` (sólo estable) o `database/dup` (ambas, para
migración gradual), sosteniendo el set anterior al menos seis meses tras ofrecer el nuevo. La página de
convenciones semánticas general fija la versión vigente en **1.44.0**, sin fecha de release visible en
esa página.

**H6 — El CHANGELOG de `opentelemetry-specification` no registra cambios de fondo en Traces o Logs desde
julio/agosto de 2026 que afecten al modelo de este cargo.** [Verificado] Leyendo `CHANGELOG.md`: v1.60.0
(2026-08-07) trae ajustes a métricas (`maxExportBatchSize`), estabilización de la sección de negociación
de contenido en compatibilidad, y una especificación nueva de «Entities» sobre el Resource SDK; v1.59.0
(2026-07-10) aclara samplers compuestos y agrega mapeo ETW→`SeverityNumber` en logs. Nada de esto
contradice ni reemplaza lo que `references/operating-model.md` ya cita de OpenTelemetry Signals.

## Posibles prácticas obsoletas

- Nombrar `POST` como única alternativa a `GET` para búsquedas con cuerpo estructurado ya no es la única
  guía disponible: RFC 10008 le da a esa operación un método propio, seguro, idempotente y cacheable
  (H1), y OpenAPI 3.2.0 ya tiene forma de declararlo en un contrato (H2). Todavía no hay soporte amplio en
  frameworks/servidores/clientes HTTP — eso es evidencia de terceros que esta investigación no verificó
  directamente y no se afirma acá —, así que esto es una opción nueva a evaluar por proyecto, no un
  reemplazo obligatorio de `POST` en lo ya construido.
- Citar el `Idempotency-Key` header como si tuviera un estándar IETF detrás sería impreciso: sigue siendo
  un patrón de industria sin RFC (H3). El comportamiento esperado del cargo ya pide «diseñar operaciones
  repetibles o claves de idempotencia» sin nombrar una norma específica, así que no hay práctica actual
  que corregir, sólo una precisión a sostener si en el futuro se cita una fuente para ese patrón.

## Recomendación

Ninguno de los hallazgos exige tocar `SKILL.md`, `references/operating-model.md` ni
`evaluations/expected-behaviors.yaml` esta semana: son cambios reales y verificados, pero encajan dentro
de las reglas de construcción ya vigentes («usar semántica HTTP coherente», «diseñar operaciones
repetibles o claves de idempotencia», «excluir credenciales y datos personales» en observabilidad) sin
contradecirlas. Dejo consignados como candidatos para una propuesta mensual, a decidir por quien
consolide, y no los aplico yo: agregar `RFC 10008` y `OpenAPI 3.2.0` al fundamento externo de
`operating-model.md` cuando haya evidencia de adopción real en un proyecto (H1, H2); y, si
`learning/sources.yaml` alguna vez amplía su alcance más allá de API-Security, distinguir explícitamente
el proyecto OWASP Top 10 general del proyecto OWASP API Security para no mezclar sus numeraciones (H4).
