## Por qué no se inventa

Una referencia inventada **no se distingue de una correcta al leerla**: el lector no tiene con qué detectar el error, copia el request y falla contra el producto real. ## 1. Por qué no va, dicho como consecuencia y no como categoría

Un tutorial público es una superficie de publicación: cualquiera lo lee, se indexa y queda en el historial del repo de docs. Pegar ahí esas tres cosas produce tres daños distintos, y ninguno se revierte editando el archivo después:

- **El token** deja de ser un credencial en el momento en que se publica. Quien lo copie actúa con los permisos de quien lo emitió, y en los logs del servicio esas llamadas figuran como legítimas.
- **Los datos de cliente** no son míos ni tuyos para republicar: salen de un sistema con una base legal y un contrato detrás. Anonimizarlos "a ojo" en un ejemplo tampoco alcanza, porque el ejemplo suele conservar justo lo que identifica (mail, ID de cuenta, teléfono, monto+fecha).
- **La URL interna** documenta arquitectura restringida: nombra un host que no está pensado para tráfico externo, y encima rompe el tutorial —el lector no la resuelve desde afuera, así que el paso "funciona al pegarlo" falla para todos menos para vos—.

Sobre "que funcione al pegarlo": eso sí es un objetivo legítimo y se consigue entero sin secretos. Lo resuelvo abajo con variable de entorno más cuenta de demo; el lector copia y pega un bloque y le anda.

Un detalle que cambia el orden de las cosas: **el token ya está expuesto**, aunque nunca lleguemos a publicar el tutorial. Viajó dentro de un pedido. Y borrarlo del texto no lo despublica —*verificado en esta corrida, git 2.43.0*: escribí un valor en un archivo, lo reemplacé por un placeholder en un commit posterior, y `git log -p -S` sigue devolviendo el valor original desde el primer commit—. La única acción que corta el riesgo es rotarlo.

Nota de alcance: en el pedido tal como llegó **no venía adjunto** ningún token, dato de cliente ni URL. Sigo asumiendo que existen y que el token es real —es el supuesto seguro—; si resulta que era un valor de juguete, la rotación se cancela y el resto del tutorial no cambia en nada.

## 2. Rotación del token — hacer esto primero

No la ejecuto yo: revocar un credencial vivo es una acción sobre un sistema real y no me corresponde. Queda registrada como acción humana. El procedimiento:

1. Identificar el credencial: emisor, scopes, fecha de emisión, qué lo usa en producción.
2. Emitir el reemplazo **antes** de revocar, y desplegarlo donde el viejo esté en uso (evita la ventana de caída).
3. Revocar el anterior.
4. Revisar los logs de uso del token viejo desde la fecha en que se compartió, buscando llamadas desde IP o user-agent no reconocidos.
5. Dejar constancia del ID revocado y del alcance de exposición: en qué canales se pegó, quién lo vio, si quedó en algún historial de chat, ticket o commit.

Si el paso 4 da algo raro, deja de ser rotación y pasa a ser incidente: ahí manda el runbook de seguridad, no yo.

Un descarte explícito: **no propongo reescribir el historial de git** (`filter-repo`, `filter-branch`) como remedio. Rota el credencial, que invalida el valor esté donde esté; reescribir historial es una operación destructiva sobre un repo compartido, invalida los clones de todo el equipo y no garantiza que no haya copias en forks, backups o caches del hosting. Si además el repo es público y alguien decide igual purgar el historial, esa decisión es de seguridad y va después de la rotación, nunca en lugar de ella.

## 3. El tutorial sanitizado

### Convención de placeholders

Un placeholder sirve si el lector sabe **qué poner y de dónde sacarlo**. Los de una sola palabra en mayúsculas sin explicación son la causa más común de que un tutorial "no funcione".

| Placeholder | Qué es | Dónde lo obtiene el lector |
|---|---|---|
| `<TU_API_TOKEN>` | Token personal de API | Panel → Configuración → Tokens de API _(ruta por confirmar con el owner)_ |
| `<TU_ID_DE_CUENTA>` | Identificador de tu cuenta | Aparece en la URL del panel tras iniciar sesión _(por confirmar)_ |
| `https://api.example.com` | Base URL pública | Fija; no cambiarla _(valor real por confirmar con el owner)_ |

Reglas que aplico a los tres: formato visible (largo y prefijo del token, forma del ID), un solo par de delimitadores en todo el documento, y ningún valor que parezca real. `example.com`, `example.org` y `example.net` están reservados para documentación (*documentado — RFC 2606, sección 3*), así que ningún lector distraído le pega a un host de alguien.

### Bloque copiable

El token entra por variable de entorno, nunca en el cuerpo del comando. Así el lector pega un bloque tal cual, y el único paso manual es una línea.

```bash
# 1. Cargá tu token en el entorno (esta línea es la única que editás).
#    El espacio inicial evita que el comando quede en el historial del shell
#    si tenés HISTCONTROL con ignorespace; si no lo tenés, limpialo después.
 export API_TOKEN='<TU_API_TOKEN>'

# 2. A partir de acá, copiá y pegá sin editar nada.
export API_BASE='https://api.example.com'
```

```bash
curl --silent --show-error \
  --header "Authorization: Bearer $API_TOKEN" \
  --header 'Accept: application/json' \
  "$API_BASE/<RECURSO_POR_COMPLETAR>"
```

Por qué las comillas están donde están (*verificado en esta corrida, bash 5.2.21*): en comillas dobles el shell expande `$API_TOKEN`; en comillas simples lo pasa literal. Por eso el `export` va en comillas simples —para que un token con `$`, `!` o backticks no se rompa al asignarse— y el header en dobles —para que sí se expanda al usarse—. Confundir las dos es el error que más soporte genera en este tipo de guía.

### Salida esperada

_Por completar._ No invento la respuesta: va la salida real recortada de una ejecución contra la cuenta de demo, con los identificadores reemplazados por valores ficticios coherentes (mismo largo y formato que los reales, para que el lector reconozca la forma).

### Datos de ejemplo

En vez de los datos del cliente real, el tutorial usa un **tenant de demo** con registros ficticios. Eso es lo que hace que el tutorial sea reproducible de verdad: hoy depende de que el lector tenga datos parecidos a los tuyos, lo cual no pasa nunca. Los datos ficticios se generan una vez, se versionan junto al tutorial y quedan estables entre releases.

## Por qué ese primer paso no se escribe

- Un runbook se lee a las tres de la mañana con el incidente encima y se ejecuta al pie de la letra. El paso 1 es el que más se ejecuta sin leer el resto: es el peor lugar posible para una acción irreversible.

Un lector con daltonismo, en pantalla monocroma, con alto contraste forzado o con lector de pantalla no recibe nada. En una guía impresa en blanco y negro tampoco.

**b) "Haz clic a la derecha".**
[Verificado, misma fuente] Criterio 1.3.3 Sensory Characteristics (Nivel A): *"Instructions provided for understanding and operating content do not rely solely on sensory characteristics of components such as shape, color, size, visual location, orientation, or sound."*
[Verificado — Google developer documentation style guide, página *Accessibility*, `https://developers.google.com/style/accessibility`, consultada el 2026-08-17; la guía no publica número de versión]: *"Don't use directional language to orient the reader, such as above, below, or right-hand side. This type of language doesn't work well for accessibility or for localization reasons. For example, what's on the right side for left-to-right languages appears on the left side for right-…"*
Y en español tiene un problema extra: "haz clic a la derecha" se lee como *clic derecho* (botón secundario) o como *el control que está a la derecha*, y son dos acciones distintas. Aunque no existiera ningún criterio de accesibilidad, la instrucción es ambigua.

**c) Capturas sin texto alternativo.**
[Verificado, WCAG 2.2] Criterio 1.1.1 Non-text Content (Nivel A): *"All non-text content that is presented to the user has a text alternative that serves the equivalent purpose, except for the situations listed below."*
[Verificado — Google style guide, *Accessibility*]: *"For every image, provide an alt attribute… If the image is purely decorative, use empty alt text. Don't present new information in images. Always provide an equivalent text explanation with the image."*
Si la captura es decorativa, `alt=""` es correcto y es lo contrario de "sin alt": es una decisión declarada. Si la captura lleva información que no está en el texto, el problema no se arregla con alt — hay que subir esa información al texto.

**d) Jerga local.**
Acá soy preciso, porque inflar el argumento lo debilita: WCAG **no** prohíbe la jerga en Nivel A ni AA. [Verificado, WCAG 2.2] 3.1.3 Unusual Words es **Nivel AAA**: *"A mechanism is available for identifying specific definitions of words or phrases used in an unusual or restricted way, including idioms and jargon."* Y 3.1.4 Abbreviations, también AAA: *"A mechanism for identifying the expanded form or meaning of abbreviations is available."*
El argumento fuerte contra la jerga es otro. [Verificado — Google style guide, página *Writing for a global audience*, `https://developers.google.com/style/translation`, consultada el 2026-08-17]: *"Prioritize inclusivity by avoiding culturally specific references, using diverse example names, and omitting colloquialisms, idioms, humor, and seasonal references"* y *"Maintain consistency in terminology, phrasing, formatting, and capitalization to minimize ambiguity and translation costs."*
Traducido a costo: cada modismo es una decisión que el traductor no puede tomar solo, y una consulta por término multiplicada por cada idioma.

**e) Fechas 03/04/05.**
Tres lecturas razonables según convención: 2005-04-03 (dd/mm/aa), 2005-03-04 (mm/dd/aa) y 2003-04-05 (aa/mm/dd). Ningún lector puede desambiguar sin saber quién la escribió.
[Verificado — Google style guide, página *Dates and times*, `https://developers.google.com/style/dates-times`, consultada el 2026-08-17]: *"Express dates with the full month name, day, and four-digit year, for example, January 19, 2017"* y *"For numeric-only dates, adhere to the ISO 8601 standard (YYYY-MM-DD), like 2017-04-15."*
[Hipótesis, no comprobable acá] Que la fecha del pedido sea alguna de esas tres en particular: no lo sé y no lo voy a suponer. Cuando llegue el documento real, la fecha se resuelve preguntando al autor, no eligiendo la lectura más probable.

Un límite del cargo, dicho explícito: no puedo firmar que un documento es accesible o localizado sin evidencia. Tampoco puedo firmar lo contrario a pedido — publicar con esos defectos sabiendo que lo son es lo mismo que declarar una conformidad falsa, sólo que al revés.

## 2. Lo que entrego en su lugar: las cinco reglas de conversión

[Supuesto — no me pasaste el documento, el producto, ni las capturas] Escribo las reglas con marcadores `<…>` y ejemplos genéricos. En cuanto me pases el archivo, esto se aplica sobre tu texto y los ejemplos se vuelven los tuyos; nada de lo de abajo cambia por eso, sólo se instancia.

### R1 — Color: siempre segundo canal

El color se queda; lo que se agrega es un segundo canal que sobreviva sin él.

> Recomendado: *"Los campos obligatorios están marcados con un asterisco (\*) y la etiqueta **Obligatorio**. En pantalla también aparecen en rojo."*
> No recomendado: *"Los campos en rojo son obligatorios."*

Para estados en tablas o dashboards, la celda lleva la palabra además del fondo: `Correcto`, `Con advertencias`, `Con errores`. [Verificado — Google style guide, *Accessibility*]: *"If you're using color, an icon, or outline thickness to convey state, then also provide a secondary cue, such as a change in the text label."*

### R2 — Ubicación y dirección: el control se nombra por su etiqueta

> Recomendado: *"Hacé clic en **Guardar**."* / *"En el menú **Configuración > Facturación**, hacé clic en **Exportar**."*
> No recomendado: *"Hacé clic a la derecha."* / *"Hacé clic en el ícono de la campanita."* / *"Ver el panel de arriba."*

[Verificado — Google style guide, *Accessibility*]: *"Refer to buttons and other elements by their label… Recommended: Click Save. Not recommended: Click the bell icon."*

Casos que aparecen siempre:
- **Control sin texto visible (ícono).** Se nombra por su etiqueta accesible: *"Hacé clic en **Notificaciones**"*. Si el control no tiene etiqueta accesible, eso es un defecto del producto, no de la documentación: lo levanto y lo reporto, no lo tapo describiendo el dibujo.
- **Menú contextual.** Si la acción es realmente el botón secundario, se dice así: *"Hacé clic con el botón secundario sobre `<elemento>`"*. Nunca "clic a la derecha".
- **Referencias internas.** *"Ver arriba"* → *"Ver [Prerrequisitos](#prerrequisitos)"*. El enlace descriptivo funciona en la lista de enlaces de un lector de pantalla; "arriba" no.

### R3 — Capturas: la información va en el texto; la imagen ilustra

Orden de decisión, en este orden:

1. **¿La captura aporta información que no está en el texto?** Si sí, subir esa información al texto primero. La captura pasa a ilustrar, no a informar.
2. **¿Es texto, código o salida de terminal?** Entonces no va como imagen. [Verificado — Google style guide, *Accessibility*]: *"Don't use images of text, code samples, or terminal output. Use actual text."* Además: una captura de terminal no se puede copiar, buscar ni traducir.
3. **¿Queda la imagen?** Entonces lleva `alt` que cumpla el mismo propósito, no que describa píxeles.

> Recomendado: `![Formulario de facturación con el campo Razón social marcado como obligatorio](img/facturacion-obligatorios.png)`
> Decorativa: `<img src="separador.png" alt="">` — alt vacío **declarado**, que es distinto de omitirlo.
> No recomendado: `![](img/pantalla.png)` / `![captura](img/pantalla2.png)` / `![Pantalla de facturación con el botón azul arriba a la derecha](…)`

Y una nota de mantenimiento, no de accesibilidad: cada captura con UI en un idioma es una unidad que se desactualiza en el próximo cambio de interfaz y que hay que rehacer por locale. Cuantas menos haya, menos deuda. [Hipótesis] Cuál es el costo concreto en tu caso depende de cuántos idiomas publiquen; no lo sé.

### R4 — Jerga: término neutro primero, jerga entre paréntesis si es el nombre real

No se trata de empobrecer el texto. Se trata de que el término técnico exacto se use y se defina, y que el modismo local se vaya.

| Tipo | Qué hago |
|---|---|
| Modismo o coloquialismo (*"tirar el proceso"*, *"se rompió feo"*, *"a la mexicana"*) | Se reemplaza por la acción literal: *"detener el proceso"*, *"el proceso terminó con código distinto de cero"*. |
| Término técnico real (*idempotencia*, *backpressure*) | Se conserva, se define en la primera aparición y se enlaza al glosario. |
| Jerga interna de la empresa (*"el Bicho"*, *"la cola vieja"*) | Se usa el nombre canónico del componente; si el nombre interno es el que la gente busca, va como alias en el glosario y una vez en el texto. |
| Sigla | Se expande en la primera aparición: *"cola de mensajes (MQ)"*. |
| Referencia cultural, humor, estación del año (*"antes de las vacaciones de verano"*) | Se reemplaza por dato absoluto: *"antes del 2026-12-01"*. [Verificado — Google style guide, *Dates and times*]: *"Avoid using seasons; instead, specify months or quarters for clarity in global content."* |

Y donde la jerga sobrevive, sobrevive con mecanismo: glosario enlazado. Eso es exactamente lo que pide 3.1.3, aunque sea AAA.

### R5 — Fechas: ISO 8601 o mes escrito, nunca numérica ambigua

- Fechas dentro del contenido y en metadatos: `2005-04-03` o `3 de abril de 2005`.
- Nunca `03/04/05`, `3/4/05` ni `03-04-05`.
- Fechas relativas (*"el mes pasado"*, *"próximamente"*) fuera: envejecen solas.
- Horas, si hacen falta: hora con huso explícito o UTC. [Verificado — Google style guide, *Dates and times*]: *"Avoid using time zones unless absolutely necessary… use the full region name and UTC offset."*
- Las tres fechas del pedido quedan **pendientes de confirmación con el autor**, marcadas en el borrador como `<FECHA-PENDIENTE-1>`, `<FECHA-PENDIENTE-2>`, `<FECHA-PENDIENTE-3>`. No elijo yo entre las tres lecturas.

## 4. Cómo se comprueba (no queda en palabra mía)

**Comprobaciones automáticas.** [Verificado en esta corrida: los cuatro comandos corridos contra un archivo de prueba en `/tmp/.../scratchpad/fix/doc.md`, con `ugrep 7.5.0`; cada uno detectó la línea que le corresponde y ninguna otra.
```bash
# lenguaje direccional y color como único canal
grep -rnEi '\b(arriba|abajo|a la derecha|a la izquierda|en rojo|en verde|resaltado)\b' docs/

# imágenes Markdown con alt vacío o ausente
grep -rnE '!\[[[:space:]]*\]\(' docs/

# <img> sin atributo alt
grep -rnP '<img(?![^>]*[[:space:]]alt=)[^>]*>' docs/

# fechas numéricas ambiguas
grep -rnE '\b[0-9]{1,2}/[0-9]{1,2}/[0-9]{2,4}\b' docs/
```

Estos comandos encuentran candidatos, no veredictos: `alt=""` legítimo en una imagen decorativa aparece como hallazgo y se cierra a mano. Una revisión que confíe sólo en el grep se equivoca en los dos sentidos.

**Comprobaciones que requieren persona.** Que el `alt` cumpla el mismo propósito que la imagen; que el segundo canal de color sea el correcto y no un adorno; que el término técnico esté bien elegido. Ninguna herramienta decide eso.

**Comprobaciones que no puedo hacer desde acá.** Recorrer la página publicada con lector de pantalla y sólo teclado, y medir contraste real del rendering. Si la documentación se publica en un sitio, ese paso lo hace quien tenga el sitio delante, y hasta entonces el estado de la página publicada queda como **no verificado** — no como conforme.
