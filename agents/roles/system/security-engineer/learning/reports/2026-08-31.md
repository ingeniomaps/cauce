## Hallazgos

### H1 — La publicación por CI cerró la brecha de credenciales de larga vida: `release.yml` usa OIDC trusted publishing y no un token en disco

- **Estado**: **cierra H1 y H2** del informe 2026-08-16.
- **Evidencia local**: `release.yml` declara `permissions: id-token: write` a nivel de job y publica con
  `npm publish --provenance` (línea 77); no hay `NPM_TOKEN` ni `.npmrc` en ese workflow. El comentario
  del propio archivo (líneas 27-29) lo dice explícito: «este repositorio no guarda un `NPM_TOKEN`, y no
  guardarlo es la mitad del punto». El acto humano que dispara la publicación es el `git push` de un tag
  `v*` (línea 7-9), y ningún workflow del repositorio empuja un tag por su cuenta (verificado: `git tag`
  sólo aparece como texto sugerido en `release-pr.yml`, dentro del cuerpo de un PR que un humano lee).
- **Lectura sobre el pedido de la semana pasada**: la recomendación #1 (migrar a OIDC) se aplicó. No se
  agregó un `environment` de GitHub con revisión requerida además del tag — el diseño trata el push del
  tag como el único gate humano (comentario de `release.yml`, líneas 3-6), lo cual es consistente con
  R10 y no es, por sí solo, un hallazgo: no hay ningún camino automatizado que pueda producir ese tag.
- **Confianza**: **alta** (código local verificado, sin inferencia).

### H2 — El camino de publicación manual sigue vivo y su guía de credenciales describe un mecanismo que npm ya revocó

- **Estado**: hallazgo nuevo; **matiza el cierre de H1** — la vía de CI se arregló, la vía manual que
  documenta `AGENTS.md` no.
- **Evidencia local**: `.env.example` (nuevo desde el informe anterior) sigue instruyendo, línea por
  línea: «Token de npm para publicar. Debe saltear 2FA: usá un token "Automation" (clásico) o uno
  "Granular" con la opción de bypass activada». `AGENTS.md`, sección «Convenciones», sigue describiendo
  el flujo `set -a; . ./.env; set +a` antes de `npm publish` como el camino soportado, con `.npmrc`
  expandiendo `NPM_TOKEN` del entorno.
- **Lo que ya se estableció la semana pasada y sigue vigente** (informe 2026-08-16, H1, confianza alta
  entonces): npm revocó permanentemente todos los tokens clásicos el 2025-12-09, y su creación ya estaba
  deshabilitada desde el 2025-11-05. No se volvió a abrir la fuente primaria esta semana para
  re-verificarlo — no cambió nada que lo pusiera en duda — así que se cita como **documentado** por el
  informe anterior, no como reverificado hoy.
- **Por qué importa igual que H1 se haya resuelto por CI**: la vía manual sigue siendo un camino de
  publicación con las mismas consecuencias que H1 describía (quien publique ejecuta código en cada
  instalación), y la guía que la acompaña recomienda algo mitad irrealizable, mitad acotado a 90 días.
  Si la vía manual sigue siendo necesaria (primera publicación, recuperación de una release fallida),
  la guía debería decir «token granular, acotado a este paquete, con expiración» — que es lo que el
  informe anterior ya recomendaba — en vez de nombrar un tipo de token que ya no se puede crear.
- **Confianza**: **alta** en el hecho local (el texto de `.env.example` y `AGENTS.md` están tal cual se
  citan); **media** en si la vía manual sigue siendo parte del flujo esperado o es documentación que
  quedó atrás de `release.yml` — no se pudo establecer sin preguntarle a quien mantiene el paquete (ver
  Preguntas abiertas).

- **El detalle que evita el riesgo residual que el informe anterior dejaba abierto**: `research-pr`

  tiene cómo lograrlo: el nombre del archivo de destino no lo elige el contenido del artifact.
