- **Estado**: hallazgo nuevo — contenido distinto al de la semana pasada.
- **Documentado, leído de cada entrada hoy**:
  - **«Node 20 is no longer available in GitHub Actions»** (2026-09-23): los runners de Actions ya no
    ofrecen Node 20 para correr JavaScript actions; la variable de escape temporal
    `ACTIONS_ALLOW_USE_UNSECURE_NODE_VERSION` dejó de existir. Afecta a quien mantiene una action que
    declara `runs.using: node20` (tiene que pasar a `node24`) y a quien fija una action vieja sin esa

    workflow declara una action propia con `runs.using`.
  - **«Security improvements for SSH»** (2026-09-22): a partir del 2027-01-13, GitHub retira claves RSA
    con firma SHA-1 (`ssh-rsa`) y el intercambio de claves `diffie-hellman-group-exchange-sha256`, sube el
    tamaño mínimo de clave RSA a 3072 bits y agrega el algoritmo post-cuántico `mlkem768x25519-sha256`.
    Afecta sólo a quien se conecta a Git por SSH; Cauce publica con `github.token` efímero por job y con
    OIDC para npm — no hay una clave SSH de mantenimiento declarada en el repositorio (`.env.example` sólo
    nombra el token granular de npm, igual que en informes anteriores).

    búsqueda literal sobre `.github/workflows/*.yml`).

### H7 — Local: el puente de Antigravity fallaba abierto ante entrada ilegible o con forma desconocida — dos guards de la misma familia que H7 de la semana pasada, cerrados en `[0.99.0]`

- **Estado**: hallazgo nuevo, local — es el más relevante de este informe para el contrato del cargo, por
  la misma razón que el H7 del 2026-09-21: toca la superficie que `SKILL.md` § Límites nombra desde el
  lado defensivo, y es un ejemplo directo de lo que R27 describe como «una defensa que se aplica por
  defecto» — acá el defecto era la forma contraria, fallar abierto.
- **Verificado hoy leyendo `docs/issues/198*.md`, `docs/issues/200*.md`, `automatization/runners/
  antigravity/hook.js` y `engine/hooks/input.js`** (no se infiere sólo del CHANGELOG):
  - **Caso 198**: `automatization/runners/antigravity/hook.js` leía stdin con su propia copia de
    `readInput`, sincrónica, cuyo `catch` cubría tanto «sin stdin» como «JSON ilegible» devolviendo `{}`
    para ambas. Un `git push --force` cuyo JSON de entrada le faltaba la última llave se interpretaba como
    comando y archivo vacíos, ningún guard tenía qué juzgar, y el puente respondía `{"decision":"allow"}`
    — reproducido en el propio caso antes del fix (`printf` con el JSON incompleto). El fix hace que el
    puente use el `readInput()` del motor (`engine/hooks/input.js`), que ya distinguía esos dos casos y
    niega el segundo por diseño («un guard que no sabe qué juzgar no autoriza», comentario de la función).
  - **Caso 200**: incluso con JSON válido, `normalize()` leía cada campo por nombre fijo
    (`toolCall.args.CommandLine`, `TargetFile`, etc.) y convertía el que no encontraba en `''`, sin
    comprobar que hubiera encontrado algo. Una llamada con un campo renombrado —`Command` en vez de
    `CommandLine`— llegaba a los guards sin comando, ninguno frenaba, y el mismo `git push --force` que el
    puente niega con el nombre de campo que reconoce pasa con cualquier otro. El fix agrega `undescribed()`:
    un `pre-shell` sin `command` o un `pre-files` sin `file_path` (tras normalizar) se niega, nombrando qué
    campos sí llegaron.
  - Los dos casos están marcados `prioridad: alta` en su frontmatter y ambos describen el mismo patrón que
    el H7 de la semana pasada en `shell.js`/`input.js`: un guard que existe para negar una acción sin
    autorización (push forzado, escritura fuera de lo esperado) fallaba **permitiendo** ante una entrada
    que no podía interpretar, en vez de negar por defecto.
- **Lo que esto no establece**: no se corrió un caso propio esta semana contra los dos —por ejemplo,
  reproducir en un banco desechable el JSON incompleto o el campo renombrado del caso 198/200 y observar
  el bloqueo con el código de `main` en vez de leer el diff—; lo verificado es que el código en el árbol
  coincide con lo que los casos y el CHANGELOG describen, no una ejecución propia que lo ejerza.
- **Confianza**: **alta** en que el código existe y coincide con la descripción, por lectura directa de
  las fuentes citadas; **sin verificar por ejecución propia** esta semana.

### H8 — Local: un `apply_patch` de Codex volvía a frenar una reversión honesta de migración, degradando a un falso positivo — sin bypass de autorización

- **Estado**: hallazgo nuevo, local, de menor relevancia que H7 — no es un fallo hacia el lado permisivo.
- **Verificado hoy leyendo `docs/issues/199*.md`**: el guard que el caso 185 arregló para juzgar sólo el
  bloque `Down`/`down` de una migración (y no frenar una reversión honesta que hace un `DROP TABLE`)

  propio `Down`. El propio caso lo describe como degradación al comportamiento anterior al 185, «no a uno

- **Relevancia para el cargo**: baja directamente, mencionado por completitud porque toca el mismo guard
  de migraciones que H10 del informe anterior; no compromete ninguna autorización.
- **Confianza**: **alta** en que el defecto y su fix están descritos como dice el caso, por lectura
  directa; **sin verificar por ejecución propia** esta semana.
