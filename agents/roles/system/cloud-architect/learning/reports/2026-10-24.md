## Hallazgos

**H1 — AWS lanzó, el 2026-10-02, un "version catalog" en AWS Health: una fuente centralizada de
información de ciclo de vida de versiones de software para Amazon RDS, Amazon EKS y AWS Lambda, con más
servicios por agregarse.** La página dedicada
(`aws.amazon.com/about-aws/whats-new/2026/10/aws-health-introduces-version-catalog-software-lifecycle-management/`,
WebFetch, esta corrida) dice textualmente: «a centralized source of lifecycle information for software
versions across AWS services», y que ayuda a los clientes a «move from reactive to proactive management
of version upgrades and end-of-support risk». En el lanzamiento inicial cubre «Amazon RDS, Amazon EKS,
and AWS Lambda with more services being added over time». Provider: AWS. Servicio: AWS Health.
Alcance: RDS, EKS, Lambda. Región: no especificada (consola de AWS Health, global). Fecha: 2026-10-02.
Estado: verificado, página dedicada del anuncio. Es relevante para el paso 6 de «Flujo de arquitectura»
(`SKILL.md`, «madurez» de un servicio administrado) y para «Resiliencia y capacidad»
(`operating-model.md`): es una herramienta del propio proveedor para hacer exactamente lo que este cargo
hace a mano en cada corrida de aprendizaje —rastrear fin de soporte antes de que llegue—, acotada a tres
servicios por ahora.

**H2 — Partner Cross-Cloud Interconnect para AWS está confirmado en GA desde el 2026-04-14 para la
variante con VPC Network Peering, y desde el 2026-09-29 para el soporte de Network Connectivity Center
(NCC); esto resuelve la pregunta abierta que dejó H3 del informe del 2026-10-02.** La página dedicada de
release notes (`docs.cloud.google.com/network-connectivity/docs/interconnect/release-notes`, WebFetch,
esta corrida) —distinta de la página conceptual de overview usada en la corrida anterior, que no
mencionaba estado ni fecha— trae tres entradas sucesivas: «Partner Cross-Cloud Interconnect for Amazon
Web Services (AWS) is available in Preview» (2025-12-09); «Partner Cross-Cloud Interconnect for Amazon
Web Services (AWS) with VPC Network Peering is Generally Available» junto con «Network Connectivity
Center (NCC) support for Partner Cross-Cloud Interconnect for Amazon Web Services (AWS) is available in
Preview» (2026-04-14); y «Network Connectivity Center (NCC) support for Partner Cross-Cloud Interconnect
for Amazon Web Services (AWS) is Generally Available» (2026-09-29). La página de release notes no trae
información sobre facturación. Un blog post dedicado a networking de Next 2026
(`cloud.google.com/blog/products/networking/whats-new-in-cloud-networking-at-next26`, WebFetch, esta

**H3 — Google Cloud respondió, el 2026-10-23, a la vulnerabilidad GCP-2026-071 en los componentes

Servicio: Cloud SQL. Región: global (parche de componente administrado, no regionalizado). Fecha:
2026-10-23. Estado: verificado, página dedicada. Es relevante para «Landing zone y seguridad»

## Posibles prácticas obsoletas

H1 no señala una práctica obsoleta; es una herramienta nueva para una práctica que este cargo ya
recomienda (rastrear fin de soporte antes del corte), acotada por ahora a RDS, EKS y Lambda.

H2 corrige, no una práctica obsoleta, sino una afirmación de estado: la recomendación del informe del
2026-10-02 de «no afirmar GA todavía» para Partner Cross-Cloud Interconnect queda superada — ya está en
GA, desde abril para la variante con VPC Peering y desde septiembre para la variante con NCC. Quien haya
leído el informe anterior y decidido esperar puede reconsiderar esa decisión con esta fecha.

H3 señala una práctica a corregir puntual y con fecha de corte ya vigente: correr Cloud SQL Auth Proxy,
Cloud SQL Proxy Operator o gcloud CLI por debajo de las versiones 2.26.3, 1.8.4 y 590.0.1 respectivamente
deja expuesta la vulnerabilidad GCP-2026-071 para quien no dependa del parcheo automático de componentes
administrados.

H4 no señala una práctica obsoleta; agrega una opción de ahorro para quien ya tenga uso sostenido de
Hyperdisk Balanced o Hyperdisk Throughput Exapool sin comprometer capacidad.

H5 no deja ninguna práctica pendiente: el proveedor ya resolvió el problema sin acción del usuario.

H6 no señala una práctica obsoleta de diseño; es un dato de mejora de resiliencia para quien modele RTO
de control plane sobre GDC bare metal con balanceo BGP empaquetado — el número de 20 segundos pasa a ser
el peor caso de versiones anteriores, no el actual.

H7 repite la misma situación de las seis corridas anteriores: no se puede confirmar ni descartar que el
corte haya ocurrido en los hechos, dentro de lo que R12 permite comprobar. La recomendación de no usar
AWS App Mesh en diseños nuevos sigue vigente, con el corte anunciado ya 24 días vencido sin ninguna
fuente pública que lo confirme o lo desmienta.

H8 no señala ninguna práctica obsoleta; confirma que el contenido de fondo de las cuatro fuentes
primarias no cambió desde la corrida anterior.

## Recomendación

1. **H1 — No requiere cambio de contrato.** Ninguna línea de `sources.yaml`, `SKILL.md` ni
   `operating-model.md` nombra AWS Health. Queda como conocimiento operativo: para cuentas AWS con RDS,
   EKS o Lambda, el version catalog es una fuente adicional para el paso 6 de «Flujo de arquitectura».
2. **H2 — No requiere cambio de contrato.** El contrato es agnóstico de proveedor a propósito y no nombra
   Cloud Interconnect. La lección operativa —que la página de release notes, no una página conceptual de
   overview, es la que sostiene estado y fecha— ya está cubierta por la oración de `learning/AUTOMATION.md`
   sobre abrir «la página o el artículo dedicado que la sostiene»: esta corrida muestra que esa página
   puede no ser la primera que parece dedicada, no que la regla esté mal escrita. No se propone una
   redacción nueva sobre un solo caso.
3. **H3 — No requiere cambio de contrato.** Ninguna línea del contrato nombra Cloud SQL Auth Proxy ni
   gcloud CLI. Queda como conocimiento operativo con fecha de corte ya vigente.
4. **H4 — No requiere cambio de contrato.** Ninguna línea del contrato nombra Hyperdisk ni CUDs de block
   storage. Queda como conocimiento operativo de costo.
5. **H5 — No requiere cambio de contrato.** El proveedor ya resolvió el problema; no hay acción ni
   contrato que ajustar.
6. **H6 — No requiere cambio de contrato.** Ninguna línea del contrato nombra Google Distributed Cloud.
   Queda como conocimiento operativo de resiliencia.
7. **H7 — No requiere cambio de contrato.** Es evidencia de que el paso 6 de «Flujo de arquitectura»
   sigue siendo la comprobación correcta; la pregunta de si el corte se cumplió en los hechos queda
   abierta para quien pueda comprobarlo con acceso real.
8. **H8 — No requiere cambio de contrato.** Confirma que `references/operating-model.md` sigue citando
   fuentes vigentes.

Ninguna de las ocho se aplica en este informe: `learning/AUTOMATION.md` restringe este ciclo a
investigación y `sources.yaml` marca `automatic_apply: false`.
