## Hallazgos

### H1 — MLflow 3.16.0 (2026-09-03) vuelve `fail-closed` el comportamiento por defecto de `basic-auth`, cerrando la causa estructural detrás de las tres advisories de autorización del informe anterior

Confianza: **alta**. Verificado, `CHANGELOG.md` crudo (`master`), entrada 3.16.0, sección «Breaking
Changes»: *"enable fail-closed authorization by default"* (PR #25308).

Verificado, PR #25308 leído directo: la variable `MLFLOW_BASIC_AUTH_FAIL_CLOSED` pasa de `False` a `True`
por defecto. Antes, una request autenticada que llegaba a una ruta sin decisión de autorización explícita
se permitía (fail-open); ahora recibe `403` (fail-closed). El propio PR condiciona el cambio a ocho PR
previos que, según su descripción, dejaron *"every Flask route family... gated"* y cobertura equivalente
para rutas FastAPI nativas, con guards de CI para prevenir rutas no gateadas en el futuro. Se marca como
cambio incompatible (rompe a un plugin de auth propio o de terceros que dependiera del fail-open previo) y
por eso entra en un release minor (3.16.0), no en un patch.

Impacto para este cargo: es la corrección estructural de la clase de falla que `evaluations/results` de
este cargo y el informe anterior (H3 de 2026-08-31) ya venían señalando —«tiene basic-auth habilitado» no
equivalía a «acceso mínimo» sin mirar versión—. No hace falta acción sobre `operating-model.md` ni
`SKILL.md`: el texto de «cadena de suministro»/«acceso mínimo» ya cubre el caso general, y este hallazgo es
evidencia de que el propio proveedor llegó a la misma conclusión por default seguro. Se registra para dejar
constancia y para no tener que re-derivar «qué versión trae este arreglo» la próxima vez.

### H3 — Las dos advisories de autorización que el informe anterior dejó sin CVE confirmado ahora lo tienen; una verificada directo en NVD, la otra sólo por agregadores de terceros

Confianza: **alta** para `CVE-2026-69148` (verificado); **media** para `CVE-2026-69146` (documentado, no
verificado directo).

**CVE-2026-69148** (GHSA-gqch-g4w5-7qcw): verificado, respuesta directa de la API REST 2.0 de NVD —
descripción confirma que `CreateModelVersion` sólo valida contención de path del `run_id`/`model_id`, sin
validar permiso de lectura sobre el run referenciado; CVSS **7.1** (`AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:L/A:N`);
publicado **2026-08-17**. Coincide con lo ya establecido la semana pasada por el advisory de GitHub; lo
nuevo es la confirmación de asignación formal en NVD.

**CVE-2026-69146** (GHSA-3p64-6gvh-82v5): documentado, vía agregadores de terceros (GitLab Advisory
Database, OpenCVE) — no se leyó la página de NVD directo para este CVE puntual. CVSS **6.5 (Medium)**:
cualquier usuario autenticado puede inyectar registros de dataset arbitrarios en el run de otro usuario
llamando `POST /api/2.0/mlflow/runs/log-inputs`, porque ese handler está ausente del mapa
`BEFORE_REQUEST_HANDLERS` de `mlflow/server/auth/__init__.py` y el hook de autorización lo saltea entero
—mientras que endpoints de escritura equivalentes en el mismo run (`log-metric`) sí devuelven `403`
correctamente—. Afecta 3.13.0–3.15.0 (mismo release de corte que las demás). No se sube a verificado
porque no se abrió NVD directo para este CVE — ver «Preguntas abiertas» 2.

Esto cierra parcialmente la «Pregunta abierta» 3 del informe del 2026-08-31 («¿están formalmente asignados
en NVD?»): sí, los dos; uno con verificación directa esta corrida, el otro con documentación de terceros
pendiente de confirmar contra la fuente primaria.
