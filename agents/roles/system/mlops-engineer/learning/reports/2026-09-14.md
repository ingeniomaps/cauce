## Hallazgos

### H1 — CISA confirma en fuente primaria que `CVE-2026-64849` entró al catálogo KEV por explotación activa, no por nominación preventiva

Confianza: **alta** para la confirmación general (verificado, alerta oficial de CISA); **documentado
(fuente secundaria)** para el detalle de que la explotación empezó «a horas» de la asignación del CVE.

Verificado, alerta de CISA (`cisa.gov/news-events/alerts/2026/08/19/...`) leída directo: *"CISA has added
one new vulnerability to its Known Exploited Vulnerabilities (KEV) Catalog, based on evidence of active
exploitation"*, listando *"CVE-2026-64849 MLflow Server-Side Request Forgery Vulnerability"*. Esto
confirma contra la fuente primaria lo que el informe del 2026-09-07 (H2) sólo tenía por la entrada del
feed JSON (fecha y plazo, sin la frase de motivo).

El detalle más específico —que la explotación activa habría empezado dentro de las horas siguientes a la
asignación del CVE, el 17 de agosto— sólo aparece en agregadores de terceros (The Hacker News y varios
blogs de seguridad), no en la alerta de CISA ni en un aviso de MLflow; se registra como documentado de
fuente secundaria y no sostiene por sí solo ningún paso de procedimiento.

Impacto para este cargo: sin cambio en la recomendación (actualizar a 3.15.0+), pero sube la confianza de
que «SSRF crítica con explotación activa» no es una clasificación automática del feed sino algo que CISA
declaró explícitamente para este CVE puntual.

### H2 — `CVE-2026-69146` queda verificado directo contra NVD, cerrando la «Pregunta abierta» 2 del informe anterior

Confianza: **alta**. Verificado, respuesta directa de la API REST 2.0 de NVD (`cveId=CVE-2026-69146`):
CVSS **6.5** (`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N`), CWE-862, publicado **2026-08-17**.
Descripción textual: *"LogInputs is absent from BEFORE_REQUEST_HANDLERS in the mlflow/server/auth
package, allowing any authenticated user to call POST /api/2.0/mlflow/runs/log-inputs for another user's
run_id and inject attacker-controlled DatasetInput records into the dataset_inputs lineage metadata
without UPDATE permission"*, resuelto en 3.15.0.

El número y el vector coinciden exactamente con lo que el informe anterior había tomado de agregadores
(GitLab Advisory Database, OpenCVE) sin verificación directa. No cambia ninguna conclusión; sí sube el
registro de H3 del 2026-09-07 de documentado a verificado.

### H4 — El tag `v3.16.0` existe, pero el `CHANGELOG.md` capturado en ese tag no incluye la entrada de 3.16.0: responde la «Pregunta abierta» 4 del informe anterior con un mecanismo parcial

Confianza: **alta** para los dos hechos verificados por separado; **hipótesis** para la explicación de por
qué ocurre.

Verificado, GitHub REST API (`git/refs/tags/v3.16.0`): el ref existe, apunta a un objeto `commit` con sha
`998f7103eb5bb305491aa6e661e3862af0a8a8ed`. Verificado, `raw.githubusercontent.com/.../v3.16.0/CHANGELOG.md`
releído: la versión más reciente que ese documento lista es **3.15.2 (2026-08-25)**; no tiene entrada
3.16.0. O sea que el tag existe y apunta a un commit real, pero el snapshot de `CHANGELOG.md` que ese commit
contiene fue tomado **antes** de que se agregara la entrada de 3.16.0 al archivo — consistente con un flujo
de release donde el tag se corta primero y el changelog se actualiza en un commit posterior, que no forma
parte del árbol del tag.

No se verificó el commit exacto que sí agrega la entrada de 3.16.0 (no hace falta para la conclusión
operativa). Hipótesis: cualquier release de este repositorio donde se necesite el `CHANGELOG.md` "tal como
lo vio" ese tag debe esperar contenido incompleto de la última versión — la fuente correcta para "qué
cambió en la versión más reciente" es `master` o la página de releases, nunca el tag pineado. Esto cierra
la «Pregunta abierta» 4 del 2026-09-07 con una explicación operable, aunque no con el commit puntual que
la origina.
