### H1 — Ninguna advisory de seguridad ni release nuevos de MLflow desde el 2026-09-14

Confianza: **alta**. Verificado, página oficial de advisories releída completa: mismas siete entradas que

### H2 — La advisory de la SSRF de webhooks (`CVE-2026-64849`) referencia un PR de endurecimiento adicional que todavía no está en ningún release etiquetado, y el campo «Patched versions» no lo refleja

Confianza: **alta** para los hechos verificados por separado; **hipótesis** para la implicación operativa
final.

Verificado, GHSA-7gwp-5pfp-969j releída completa: el campo **«Patched versions» dice únicamente `3.15.0`**,
sin fecha de actualización distinta de la de publicación (2 de agosto de 2026). La propia descripción de
la advisory, sin embargo, enumera tres PR: **#20747** (guard original, incompleto), **#24258** (el fix
citado por el catálogo KEV de CISA en su campo `notes` — ver H3, título verbatim *"Fix DNS-rebinding SSRF
bypass in webhook delivery"*) y **#25568**, descrito como *"Reject IPv6-transition addresses embedding
private IPv4 in webhook SSRF guard"*.

Verificado, PR #25568 leído directo: corrige que direcciones de transición IPv6 —IPv4-mapeadas
(`::ffff:100.64.0.1`) o con prefijo NAT64 (`64:ff9b::169.254.169.254`)— pueden decodificar una IPv4 privada
sin que el guard existente la detecte. **Fecha de merge: 2026-09-03**, el mismo día del release 3.16.0.

Verificado por comparación directa de fuente fijada a tag: `mlflow/webhooks/ssrf.py` en el tag `v3.15.0`
ya implementa la validación de IP del socket conectado (el fix de #24258, DNS-rebinding); el mismo archivo
en el tag **`v3.16.0` no contiene ninguna referencia a `::ffff:` ni a `64:ff9b::`** — o sea, la lógica de
#25568 no forma parte de ese release, aunque se haya mergeado a `master` el mismo día. Verificado también,
`CHANGELOG.md` de `master`: la entrada de 3.16.0 no menciona SSRF, IPv6 ni el PR #25568 (sí menciona otros
dos cambios de webhooks, ninguno de seguridad — ver «Evidencia»).

Hipótesis (no comprobable sin ver el próximo release etiquetado): mientras #25568 no aparezca en un tag,
cualquier instalación que haya seguido la recomendación de este cargo desde el 2026-08-31 —«actualizar a
3.15.0+»— sigue expuesta a la variante de la SSRF que usa direcciones de transición IPv6 para esconder un
target privado, aunque esté al día con el «Patched versions» declarado por la propia advisory. No cambia
la recomendación operativa de fondo (3.15.0+ sigue siendo estrictamente mejor que versiones anteriores, y
cierra el vector de DNS-rebinding/redirect que es el que CISA calificó de explotación activa), pero
introduce un matiz que ningún informe anterior de este cargo había registrado: el campo «Patched versions»
de una advisory no es necesariamente el techo de lo que esa misma advisory documenta como pendiente. Ver
«Preguntas abiertas» 3 y «Posibles prácticas obsoletas».

## Posibles prácticas obsoletas

Nueva esta corrida, derivada de H2: **leer el campo «Patched versions» de una advisory de GitHub como el
límite superior de lo que esa vulnerabilidad necesita** es una práctica que puede quedar corta cuando la
propia advisory referencia, en su lista de PR, un endurecimiento posterior que todavía no llegó a ningún
release etiquetado. Para este cargo —que audita cadena de suministro y decide cuándo una versión "cierra"
un CVE— la consecuencia operativa es leer también los PR referenciados por la advisory (no sólo el campo
estructurado), y no dar por completo un CVE mientras alguno de esos PR siga sin aparecer en el
`CHANGELOG.md` de un release etiquetado.

Se mantiene, sin cambio, la práctica ya señalada en las tres corridas anteriores («leer 'tiene basic-auth
habilitado' como 'acceso mínimo' sin mirar versión») y la precisión del 2026-09-14 sobre no fijar la
lectura del `CHANGELOG.md` a un tag de release específico.
