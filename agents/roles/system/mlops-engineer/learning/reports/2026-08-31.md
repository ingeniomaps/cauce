## Hallazgos

### H1 — CVE-2026-64849: SSRF crítica sin autenticación en webhooks de MLflow, explotada activamente, en el catálogo KEV de CISA con vencimiento 2026-09-02

Aplica a: MLflow < 3.15.0. Confianza: **alta**.

GHSA-7gwp-5pfp-969j (verificado, GitHub Advisory Database): CVSS **9.3 (Critical)**,
`AV:N/AC:L/PR:N/UI:N` — el endpoint no autenticado `POST /api/2.0/mlflow/webhooks/{id}/test` refleja la
respuesta upstream al llamador. `_validate_webhook_url` valida la URL inicial del webhook contra IPs
internas/privadas, pero cuando el servidor sigue una redirección HTTP durante la entrega **no revalida el
destino de la redirección**: un atacante aloja un endpoint público que responde con `302` hacia
`http://169.254.169.254/...` (metadata de nube) o `127.0.0.1`, y MLflow lo sigue sin volver a chequear.
Alcance: lectura completa de la respuesta interna, sin autenticación, en cualquier instalación por
defecto.

Catálogo KEV de CISA, feed JSON leído directo (verificado): `cveID: "CVE-2026-64849"`,
`vendorProject: "MLflow"`, `dateAdded: "2026-08-19"`, `dueDate: "2026-09-02"`. Ese vencimiento es en
**dos días** desde la fecha de este informe. Corroborado por búsqueda general (no fuente primaria propia,
documentado): explotación activa detectada horas después de asignado el CVE (17 de agosto), agencias de
prensa de seguridad (SecurityWeek, TheHackerNews, Decipher) reportan robo de credenciales de nube como
consecuencia observada.

Parche: versión **3.15.0** (2026-07-31), confirmado por el propio `CHANGELOG.md`.

Impacto para este cargo: toca directo «Proteger la cadena de suministro» de `operating-model.md`
(«origen, integridad... acceso mínimo») y R12 de este repositorio (sistemas externos reales). Cualquier
tracking server de MLflow anterior a 3.15.0 alcanzable desde una red con acceso a metadata de nube es
explotable sin credenciales; no es una recomendación de upgrade optativa, es la misma clase de hallazgo
que el SKILL.md pide no ocultar.

### H2 — GHSA-gqvg-gmmx-x4hm: el flavor `statsmodels` de MLflow ejecuta código arbitrario aunque `MLFLOW_ALLOW_PICKLE_DESERIALIZATION=False` esté activo

Aplica a: MLflow >= 2.1.0, < 3.15.0. Confianza: **alta**.

Verificado, cita literal del advisory oficial (github.com/mlflow/mlflow/security/advisories/GHSA-gqvg-gmmx-x4hm):
CVSS **8.8 (High)**, `AV:N/AC:L/PR:N/UI:R`. Otros flavors (ejemplo citado: sklearn) implementan la guarda
`if (not MLFLOW_ALLOW_PICKLE_DESERIALIZATION.get() and not is_in_databricks_runtime()...)` antes de
deserializar. La función `_load_model()` de `mlflow/statsmodels/__init__.py` (líneas 307-320 según el
advisory) llama directo a `smio.load_pickle(path)` sin ninguna guarda: el flag de seguridad, pensado como
control global, no cubre este flavor. Un artefacto de modelo malicioso subido a un artifact store
accesible ejecuta código arbitrario en cuanto alguien llama `mlflow.pyfunc.load_model()`, con el flag de
seguridad activo y sin que nada lo avise.

Impacto para este cargo: es exactamente el caso que `operating-model.md` nombra bajo «cadena de
suministro» («integridad», «escaneo») y que el SKILL.md prohíbe asumir resuelto («No acceder... entrenar,
evaluar o registrar datos/modelos reales sin autorización» presupone que cargar un artefacto es seguro si
el flag está puesto; este caso muestra que ese supuesto es falso para un flavor concreto). Ver «Posibles
prácticas obsoletas» 1.

### H3 — Tres advisories más de julio/agosto 2026, todas de autorización, todas parcheadas en la misma 3.15.0

Aplica a: MLflow < 3.15.0. Confianza: **alta** para las tres, por advisory oficial u origen directo.

- **PR #24571** (verificado, leído directo): el plugin `basic-auth` no reconocía la ruta
  `GET /mlflow-artifacts/presigned/` como ruta de artefacto proxeada, así que un usuario autenticado sin
  permiso de lectura sobre un experimento podía obtener una URL de descarga directa a almacenamiento en
  la nube de artefactos de **otro** experimento. *"An authenticated user lacking experiment permissions
  could obtain a direct cloud-storage download URL for another experiment's artifacts"* (cita literal del
  PR). Corregido extendiendo `_is_proxy_artifact_path()`.
- **GHSA-gqch-g4w5-7qcw / CVE-2026-69148** (documentado, cruzado entre la página de advisories del propio
  repositorio y un tracker de terceros — CVSS 7.1/High, `AV:N/AC:L/PR:L/UI:N`): `_validate_source_run` y
  `_validate_source_model` verifican que el artifact URI de una `CreateModelVersion` esté dentro del
  directorio del run/modelo referenciado, pero no verifican permiso de **lectura** sobre ese run. Con
  permiso `MANAGE` sobre el modelo registrado propio (que se obtiene automáticamente al crearlo), un
  usuario lee archivos arbitrarios del directorio de artefactos de otro usuario vía
  `GET /model-versions/get-artifact`, evitando el gate de lectura a nivel experimento.
- **GHSA-3p64-6gvh-82v5** (documentado, listado en la página oficial de advisories): «LogInputs endpoint
  bypasses per-run UPDATE authorization in MLflow basic-auth», severidad Moderate.

Las tres se publicaron entre el 27 de julio y el 4 de agosto de 2026 y las tres cierran en la misma
versión, 3.15.0. Impacto para este cargo: en una instalación con RBAC vía `basic-auth`, la superficie de
autorización del propio plugin de control de acceso tuvo tres agujeros independientes a la vez — vale como
ítem a mirar antes de asumir que «tiene basic-auth habilitado» equivale a «acceso mínimo» sin revisar
versión.

### H5 — Alias de MLflow: la resolución «al próximo `load_model()`» está documentada; el caso de un proceso de serving ya cargado en memoria sigue sin establecerse

Aplica a: `models:/<nombre>@<alias>`. Confianza: **alta** para lo documentado; **hipótesis** para el resto,
igual que la dejó la respuesta del cargo al caso 07.

Documentado, cita literal (mlflow.org/docs/latest/ml/model-registry/workflow/): *"Note that model alias
assignments can be updated independently of your production code. If the champion alias in the snippet
above is reassigned to a new model version in the Model Registry, the next execution of this snippet will
automatically pick up the new model version."* Esto establece que **cada llamada a la función de carga**
resuelve el alias contra su valor vigente en ese momento — no que un objeto de modelo ya instanciado en un
proceso de serving de larga duración se actualice solo. La documentación oficial no trata ese segundo
caso en ningún lugar de las páginas leídas.

Una discusión de la comunidad (github.com/mlflow/mlflow/discussions/8905, **hipótesis, no habilitante**:
sin confirmación de mantenedores, versiones citadas 0.24.2 y 2.3.1 —viejas frente a la 3.15.x vigente— y
sobre un mecanismo de módulos Python custom, no sobre el flujo estándar de alias) describe que el primer
modelo cargado en una aplicación puede quedar cacheado y que llamadas posteriores sigan usando su código
aunque se cargue un modelo distinto en la misma variable. No se toma como establecido: es un reporte
aislado, sin reproducción propia, sobre un mecanismo distinto (módulos custom, no resolución de alias).

Esto **cierra parcialmente** la pregunta abierta de `evaluations/results/2026-08-23-3.md`: confirma que la
documentación oficial no cubre el caso de proceso de serving ya cargado — el rótulo «no establecido» que
dio esa respuesta seguía siendo correcto, no fue conservador de más. Lo que agrega esta corrida es la cita
exacta de qué sí está documentado (`load_model()` por llamada) para no tener que re-derivarlo la próxima
vez. Sigue abierto qué hace en concreto el servidor de `mlflow models serve` entre requests — ver
«Preguntas abiertas» 1.

## Posibles prácticas obsoletas

1. **Asumir que `MLFLOW_ALLOW_PICKLE_DESERIALIZATION=False` alcanza para todos los flavors de MLflow.**
   H2 muestra que no cubrió `statsmodels` hasta 3.15.0. El texto de `operating-model.md` sobre cadena de
   suministro («escaneo») ya es lo bastante general como para no necesitar una regla nueva, pero quien lo
   lea debería esperar que un flag de seguridad global de un framework se verifique por flavor, no se dé
   por hecho.
2. **Leer «tiene basic-auth habilitado» como equivalente a «acceso mínimo» sin mirar versión.** H3 muestra
   tres agujeros de autorización distintos dentro del propio plugin de RBAC, activos hasta 3.15.0.

## Recomendación

Para la propuesta mensual de `learning/proposals/`, sujeta a aprobación humana. Ninguna de estas toca
`SKILL.md` — el SKILL.md ya nombra las conductas correctas («no ocultar... incidente»,«proteger la cadena
de suministro»); lo que falta es soporte de fuente, no una regla nueva.

**1. Agregar a `sources.yaml` una fuente de advisories de seguridad de MLflow.** Hoy `sources.yaml` sólo
tiene `MLflow documentation` (tier platform) y `MLflow releases` (tier project, topics versiones/cambios
incompatibles); ninguna entrada cubre seguridad. Candidato:
`{name: MLflow Security Advisories, url: "https://github.com/mlflow/mlflow/security/advisories", tier: project, topics: [seguridad, cadena-de-suministro]}`.
H1+H2+H3 de este informe —cuatro advisories en cinco semanas, una con explotación activa y plazo de CISA—
son evidencia concreta de que esa fuente falta, no una suposición.

**2. Considerar agregar el catálogo KEV de CISA como fuente transversal**, no específica de MLflow —igual
que `evaluations/results` de otros cargos (ejemplo: qa-engineer ya sigue advisories de CSA Singapur). El
feed JSON primario (`cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`) se leyó sin
bloqueo esta corrida; la página HTML equivalente dio 403.

**3. Ninguna acción sobre H5, H6 o H7 todavía.** H5 deja una pregunta abierta que no se puede cerrar sin
un entorno con MLflow corriendo (ver «Preguntas abiertas» 1); H6 es una función nueva de un solo release,
sin uso ni contrato que la fuerce; H7 confirma que el fundamento externo actual sigue vigente y no
requiere edición.
