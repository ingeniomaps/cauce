## Hallazgos

- **H1.** El dist-tag `latest` del registro de npm sigue apuntando a `12.0.2`, igual que en el informe
  anterior. Registro: **Verificado** (`registry.npmjs.org/npm/latest`, consultado 2026-09-01).
  `package.json:44` sigue fijando `packageManager: "npm@11.16.0"`, sin cambios. El entorno de este job
  reporta npm `11.17.0` — un patch por encima del pin declarado en el manifest y todavía por debajo de
  v12 — dato entregado por quien encargó la corrida, que no pude reproducir de forma independiente.
  Impacto: bajo y sin cambios respecto al 2026-08-31 — v12 aún no aplica en ningún entorno de este
  repositorio, que sigue sin dependencias de terceros (`AGENTS.md`) cuyos scripts de instalación los
  nuevos defaults de v12 pudieran bloquear. Queda como pregunta abierta por qué el job mide un patch
  distinto al fijado en `packageManager`.
- **H2.** GitHub anunció, dentro de su "2026 security roadmap" (publicado 2026-03-26), un mecanismo de
  bloqueo de dependencias de workflow: una sección `dependencies:` que fija por SHA todas las
  dependencias directas y transitivas de un workflow, con verificación de hash antes de correr el job.
  La herramienta que lo implementa, `gh-actions-lock`, está en **Technical Preview, pre-1.0**: su propio
  README declara que "the lockfile format, command flags, and behavior may change without notice
  between releases". Registro: **Documentado** (roadmap oficial + README del repositorio, sin probar la
  herramienta). Impacto: este repositorio ya fija cada acción por SHA a mano, con la versión en un
  comentario (`.github/workflows/*.yml`) — es exactamente el problema que este mecanismo declarativo
  resuelve — pero adoptarlo hoy significaría depender de una herramienta pre-1.0 cuyo formato puede
  cambiar sin aviso; no es una recomendación de adopción inmediata.
- **H3.** GitHub cambió, desde el 2026-04-23, el formato del subject claim de los tokens OIDC de Actions
  para incluir IDs inmutables de owner y repositorio además del nombre mutable (por ejemplo
  `repo:octocat@123456/my-repo@456789:ref:...` en vez de `repo:octocat/my-repo:ref:...`). El cambio es
  automático para repositorios nuevos o renombrados desde el 2026-07-15, y opt-in para los existentes.
  Registro: **Documentado** (GitHub Changelog, 2026-04-23). Impacto: `release.yml` de este repositorio
  usa OIDC trusted publishing hacia npm (`id-token: write`, sin `NPM_TOKEN` guardado —
  `release.yml:29`) — el mecanismo que este cambio afecta. `ingeniomaps/cauce` no fue renombrado ni
  creado después del 2026-07-15, así que sigue en el formato de subject claim anterior salvo opt-in
  explícito, que no se hizo. No pude establecer, con las fuentes que consulté, si la configuración de
  trusted publisher que npm ya tiene guardada para este paquete depende de ese formato o le es
  indiferente; queda en Preguntas abiertas.
- **H4.** Las acciones fijadas por SHA en los workflows de este repositorio siguen en su último release
  publicado, sin drift respecto al informe del 2026-08-31: `actions/checkout` → `v7.0.1`
  (2026-07-20T15:10:05Z), `actions/setup-node` → `v7.0.0` (2026-07-14T02:46:05Z),
  `actions/upload-artifact` → `v7.0.1` (2026-04-10T17:31:14Z), `actions/download-artifact` → `v8.0.1`
  (2026-03-11T15:44:25Z). Registro: **Verificado** (campos `tag_name`/`published_at` de
  `releases/latest` vía `api.github.com`, consultados 2026-09-01 — no de la página HTML de releases,
  que para `download-artifact` devolvió un resumen con el año incorrecto en una consulta preliminar de
  esta misma sesión y se descartó a favor del JSON de la API).
- **H5.** DORA Capabilities, la especificación SLSA (v1.2, "Approved", sin cambios desde la última
  release candidate) y el blog de OpenTofu (última entrada 2026-05-14) no muestran contenido nuevo
  desde el informe del 2026-08-31. Registro: **Verificado** para la ausencia de cambio en estas tres
  fuentes puntuales, en la fecha de esta consulta (2026-09-01) — no descarta cambios en partes de cada
  sitio que no forman parte de las páginas revisadas.

## Posibles prácticas obsoletas

No encontré, en este ciclo, una práctica de este repositorio marcada como obsoleta por evidencia
primaria. H2 describe una alternativa declarativa al pin manual por SHA que ya se usa acá, pero la
herramienta que la implementa está en preview pre-1.0 — adoptarla ahora sería reemplazar una práctica
estable por una que sus propios autores describen como inestable, no una mejora sin costo.

## Recomendación

- De H1: sin cambios respecto a la recomendación del 2026-08-31 — evaluar el pin de `packageManager` a
  npm v12 recién cuando se decida adoptar sus defaults de seguridad, corriendo antes
  `npm approve-scripts --allow-scripts-pending` para confirmarlo en concreto. No es urgente.
- De H2: no adoptar `gh-actions-lock` todavía — queda como algo para revisar cuando salga de Technical
  Preview. Mientras tanto, el pin manual por SHA que ya usa este repositorio cubre la misma superficie
  de riesgo (reproducibilidad de la dependencia) sin depender de una herramienta pre-1.0.
- De H3: no hay acción de código que tomar mientras este repositorio no se renombre ni se transfiera de
  organización. Si en algún momento se planea uno de esos dos cambios, conviene resolver antes la
  pregunta abierta en H3 sobre cómo lo toma la configuración de trusted publisher de npm, en vez de
  descubrirlo en medio de una publicación fallida.

  resolviendo una versión distinta a la declarada o si el dato de entorno correspondía a otro paso del

- H3: si la configuración de trusted publisher que npm ya tiene guardada para `@ingeniomaps/cauce`
  matchea por nombre mutable de owner/repo, por ID inmutable, o por ambos, y qué pasaría con una
