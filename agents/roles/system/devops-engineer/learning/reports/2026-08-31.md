## Hallazgos

- **H1.** npm v12 (última `12.0.2`) desactiva por defecto la ejecución de scripts de instalación
  (`preinstall`/`install`/`postinstall`) y cambia `--allow-git` y `--allow-remote` a `none`. GitHub
  recomienda subir primero a npm `11.16.0` — exactamente la versión que este repositorio ya fija en
  `packageManager` (`package.json:44`) — antes de adoptar v12. Registro: **Documentado** (changelog
  oficial de GitHub, no reproducido localmente). Impacto en este repo: bajo — AGENTS.md declara cero
  dependencias de runtime y desarrollo, así que no hay scripts de instalación de terceros que
  `allowScripts` pudiera bloquear — pero el pin actual queda un escalón por debajo de la versión que ya
  circula.
- **H2.** Dependabot aplica desde el 2026-07-14 una demora por defecto de 3 días (patch), 7 (minor) y
  30 (major) antes de abrir un PR de actualización de versión, sin necesitar configuración; las
  actualizaciones de seguridad no se demoran. Registro: **Documentado**. Impacto: bajo — el único
  `package-ecosystem` configurado en `.github/dependabot.yml` es `github-actions` (mensual), y el
  comportamiento nuevo es un default de la plataforma, no algo que este repositorio deba cambiar.
- **H3.** GitHub "Immutable Releases" está disponible de forma general desde 2025-10-28: impide borrar o
  mover tags de una release publicada y modificar sus assets. El ataque a `trivy-action` (marzo 2026,
  force-push sobre 75 de 76 tags de versión) y la campaña "Megalodon" (mayo 2026) explotaron
  precisamente la mutabilidad de tags. Registro: **Documentado** para la mecánica de la función
  (changelog oficial); la atribución del ataque a `trivy-action` sale de cobertura de prensa
  especializada (SecurityWeek, Security Boulevard), no de un advisory primario que haya podido leer, así
  que esa parte queda como corroboración secundaria. Impacto: `release.yml` de este repositorio publica
  el paquete npm y crea la GitHub Release a partir de un tag `v*` empujado por una persona
  (`release.yml:9`, `release.yml:85`); un tag de esta naturaleza es el mismo tipo de artefacto que la
  función protege.
- **H4.** SLSA pasó de v1.1 a v1.2 (estado "Approved") agregando el "Source Track", enfocado en asegurar
  el proceso de desarrollo del código fuente además del build. Registro: **Documentado** (spec pública);
  no evalué el detalle de sus requisitos contra el flujo de branch protection/CODEOWNERS de este repo
  (queda en Preguntas abiertas).
- **H5.** El 2026-05-11 un gusano (campaña "Mini Shai-Hulud", grupo reportado como TeamPCP) publicó 84
  versiones maliciosas sobre 42 paquetes `@tanstack/*` con atestación SLSA Build Level 3 y firma Sigstore
  válidas — el primer caso documentado de paquetes maliciosos con provenance válida (CVE-2026-45321 /
  GHSA-g7cv-rxg3-hmpx). El vector fue una configuración insegura de `pull_request_target` combinada con
  cache poisoning y extracción del token OIDC en memoria del runner, no una falla del mecanismo de
  provenance en sí. Registro: **Documentado** (GHSA oficial, corroborado por un segundo análisis
  independiente). Impacto: este repositorio publica con `npm publish --provenance` vía trusted publishing
  OIDC (`release.yml:29`, `release.yml:77`) y no dispara ningún workflow con `pull_request_target`
  (verificado por búsqueda en `.github/workflows/*.yml`: la única mención es un comentario en
  `sign-proposal.yml`, no un trigger) — no queda expuesto al vector concreto de este incidente, pero el
  hallazgo es relevante como referencia sobre los límites de la provenance como señal de confianza.
- **H6.** Node.js 24 ("Krypton") es la línea Active LTS actual; Node 26 es "Current" desde 2026-05-05 y
  Node.js recomienda producción sólo sobre LTS. Registro: **Verificado** (nodejs.org, consultado
  2026-08-31). El `engines.node` de `package.json` exige `>=24`, alineado con la recomendación vigente.
- **H7.** Las acciones fijadas por SHA en los workflows de este repositorio están todas en su último
  release publicado: `actions/checkout@v7.0.1` (2026-07-20), `actions/setup-node@v7.0.0` (2026-07-14),
  `actions/upload-artifact@v7.0.1` (2026-04-10), `actions/download-artifact@v8.0.1` (2026-03-11).
  Registro: **Verificado** (API de releases de cada repositorio, consultada 2026-08-31, comparada contra
  los SHA/versión comentados en `.github/workflows/*.yml`). No hay drift que corregir.

## Posibles prácticas obsoletas

No encontré, en este ciclo, una práctica de este repositorio que la evidencia recogida marque como
obsoleta con evidencia primaria. Lo más cercano es H1: el pin de `packageManager` a `npm@11.16.0`
(package.json:44) es hoy la versión recomendada de transición, no una versión obsoleta — se volvería la
práctica a revisar recién cuando el repositorio decida adoptar el comportamiento de npm v12.

## Recomendación

- De H3: evaluar habilitar "Immutable Releases" a nivel de repositorio u organización para
  `ingeniomaps/cauce`. Es un cambio de configuración de GitHub (no de archivos versionados), fuera del
  alcance de esta automatización — requiere decisión y acción humana en Settings del repositorio.
- De H1: cuando se decida adoptar npm v12, correr primero `npm approve-scripts --allow-scripts-pending`
  para confirmar en concreto que no hay scripts de instalación dependientes del comportamiento actual
  (la expectativa, dado el estado de cero dependencias del repositorio, es que no haya ninguno) antes de
  mover el pin de `packageManager`. No es urgente: npm `11.16.0` sigue siendo la versión que el propio
  changelog de npm v12 recomienda como paso previo.
