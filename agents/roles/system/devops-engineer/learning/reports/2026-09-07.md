## Hallazgos

- **H1.** El pin `packageManager: npm@11.16.0` (`package.json:44`) no lo hace cumplir nada en la CI de
  este repositorio: `.github/workflows/ci.yml` usa `actions/setup-node@v7.0.0` sin ningún paso
  `corepack enable` (búsqueda de `corepack` sobre todo el repositorio: cero resultados), y ese campo en
  `setup-node` sólo decide si se activa el caché de npm, no qué versión se instala. El npm que
  efectivamente corre es el que trae empaquetada la versión de Node.js del runner. Para Node 24.20.0 —la
  que mide este mismo job— eso es npm `11.19.0`, tres versiones menores por delante del pin declarado.
  Registro: **Verificado** (release notes oficiales de `nodejs/node` v24.20.0, que documentan "upgrade
  npm to 11.19.0 (npm team) [#64883]" como el último bump de esa serie, coincide con la versión que este
  job midió; README de `actions/setup-node`, que documenta que el campo sólo habilita caché). Impacto:
  bajo en este ciclo — sin dependencias de terceros no hay instalación cuyo comportamiento diverja por
  versión de npm — pero el pin aparenta un control que no ejerce, y la brecha entre lo declarado y lo que
  corre crece sola en cada bump de Node sin que nada lo señale.
- **H2.** Corepack —el mecanismo que, si se habilitara, sí haría cumplir `packageManager`— dejó de
  distribuirse junto con Node.js a partir de la serie 25. El propio repositorio de Corepack lo declara:
  "Corepack is distributed with Node.js from version 14.19.0 up to (but not including) 25.0.0". El
  commit `fa834896c8` sobre `doc/api/corepack.md` en `nodejs/node` agrega: "Corepack itself will no
  longer be distributed with future versions of Node.js", y el issue `nodejs/nodejs.org#7555` documenta
  el mismo retiro con el título "Corepack won't be distributed with Node.js 25+ official distributions".
  Después de esa versión, usarlo exige instalarlo aparte (`npm install -g corepack`). Registro:
  **Documentado** (fuentes oficiales de `nodejs/corepack` y `nodejs/node`; no reproducido localmente
  porque este repositorio corre sobre Node 24). Impacto: si en algún momento se decide resolver H1
  habilitando Corepack, conviene saber que la vía "viene incluido con Node" tiene fecha de vencimiento —
  `engines.node` de este repositorio exige `>=24` (`package.json`), así que hoy no afecta, pero afectaría
  a una futura migración a Node 25.
- **H3.** GitHub publicó actualizaciones a Actions el 2026-09-03 —posteriores al corte del informe
  anterior (2026-08-31)—: un permiso nuevo `vulnerability-alerts` para `GITHUB_TOKEN` (valores `read` o
  `none`) que da acceso de sólo lectura a alertas de Dependabot sin requerir un scope más amplio; una API
  REST de deprecación de runners (`GET /actions/runners/deprecations/{version}`); y cuatro propiedades
  nuevas del contexto `job` (`job.workflow_ref`, `job.workflow_sha`, `job.workflow_repository`,
  `job.workflow_file_path`) para que un reusable workflow conozca su propio origen en tiempo de
  ejecución. Registro: **Documentado** (changelog oficial de GitHub, 2026-09-03). Impacto: nulo en este
  ciclo — ningún workflow de este repositorio usa `workflow_call` (verificado por búsqueda sobre
  `.github/workflows/*.yml`), ninguno lee alertas de Dependabot, y los seis ya declaran `permissions:
  contents: read` como único permiso de nivel de workflow (verificado por búsqueda de `^permissions:`
  sobre los mismos archivos). Queda disponible si algún workflow futuro necesitara leer alertas de
  Dependabot sin ampliar permisos.
- **H4 (confirmación, sin cambio).** Los cuatro pines por SHA de `actions/checkout`, `actions/setup-node`,
  `actions/upload-artifact` y `actions/download-artifact` siguen siendo, esta semana, el último release

## Posibles prácticas obsoletas

- De H1: fijar `packageManager` en `package.json` sin un paso que lo haga cumplir (`corepack enable` u
  otro) es una práctica que aparenta un control —"este repositorio corre con npm 11.16.0"— que hoy no
  ejerce ninguno de los workflows de este repositorio. No es un riesgo activo mientras el repositorio
  tenga cero dependencias, pero es exactamente el tipo de brecha silenciosa que un lector del `package.json`
  no tiene cómo detectar sin comprobar, como se comprobó acá, qué versión corre realmente en CI.

## Recomendación

- De H1: decidir entre dos caminos, ninguno urgente mientras el repositorio no tenga dependencias de
  terceros — (a) agregar `corepack enable` a los workflows que corren `npm run ci` para que el pin de
  `packageManager` sea real, o (b) si no se lo va a hacer cumplir, quitarlo de `package.json` para no
  sugerir un control inexistente. Es una decisión de mantenimiento de este repositorio, no una urgencia de
  seguridad.
- De H2: si se opta por (a) en la recomendación anterior, registrar que Corepack sólo viene incluido con
  Node hasta la serie 24 — una futura migración a Node 25 (hoy "Current", no LTS) necesitaría agregar
  `npm install -g corepack` de forma explícita en los workflows para no perder el mecanismo.
- De H3: ninguna acción requerida ahora. Si en el futuro un workflow necesita leer alertas de Dependabot
  (por ejemplo, para bloquear un release con vulnerabilidades abiertas), usar el permiso
  `vulnerability-alerts: read` nuevo en vez de ampliar el scope del `GITHUB_TOKEN`.
