# No puedo armar ese plan, y el motivo no es una política nuestra

El pedido tenía una forma concreta: publicar el contenido correcto **encima** de la 4.2.0 y avisar por el changelog, para que quien ya actualizó quede bien sin mover el número. Esa operación no existe en el registry público de npm.

> "The publish will fail if the package name and version combination already exists in the specified registry."
> "Once a package is published with a given name and version, that specific name and version combination can never be used again, even if it is removed with `npm unpublish`."
> — docs empaquetadas con npm CLI 11.16.0, `commands/npm-publish.md` [verificado, leído localmente hoy]

> "Once `package@version` has been used, you can never use it again. You must publish a new version even if you unpublished the old one."
> — https://docs.npmjs.com/policies/unpublish [verificado, consultado el 2026-08-23]

El `npm publish` de la 4.2.0 corregida falla, y el rodeo "la bajo y la vuelvo a subir" tampoco existe: el par nombre+versión queda quemado aunque se desapublique.

**Y aunque el registry lo permitiera, no conseguiría lo que se quería.** El objetivo era que quien ya instaló quedara bien sin tocar nada, y eso no pasa por tres razones independientes:

1. Quien ya instaló tiene el tarball malo desempaquetado en su `node_modules` y en su caché. Nada lo vuelve a bajar solo: tiene que reinstalar, exista o no una 4.2.0 corregida.
2. Quien tiene lockfile guardó el `integrity` sha512 del tarball publicado. Un tarball distinto bajo la misma versión no coincide con ese hash y su `npm ci` **rompe**. Mutar la versión no los arregla: les rompe el build. [verificado: `npm-publish.md` y `configuring-npm/package-lock-json.md`, npm 11.16.0]
3. El changelog no dispara ninguna reinstalación. Los únicos avisos que llegan solos a la máquina de quien instala son la versión nueva bajo `latest` y el mensaje de `npm deprecate`; a quien ya instaló sólo lo alcanza un aviso directo.

Conclusión operativa: **los afectados se van a mover a una versión nueva sí o sí.** Lo único que decidimos hoy es si se la damos hoy.

# Lo que sí resuelve el problema de marketing

La 4.2.1 es un patch de semver: no cambia una sola promesa de lo que se anunció como "4.2". El anuncio no se rehace. Lo que se corrige es la instrucción de instalación puntual: donde la documentación diga `4.2.0`, que diga `4.2.1` o `npm i <paquete>@latest`. Es una edición de una línea, no una campaña nueva. Va como **propuesta**: el texto y quién comunica lo aprueba Producto/Marketing (fila HA-4), y no mando comunicaciones externas ni release notes sin esa aprobación.
