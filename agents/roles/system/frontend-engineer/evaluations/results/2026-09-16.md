## Lo que encontré leyendo el componente

**1. Falta el import de `useState`.** El archivo tal como me llegó empieza en `export function FormularioAlta(...)` y usa `useState` tres veces (líneas 2-4) sin importarlo ni importar nada. **2. El error del servidor se renderiza como HTML.** Línea 24: `<div dangerouslySetInnerHTML={{ __html: error }} />`, y ese `error` viene del servidor (línea 16). La documentación de React sobre esa prop dice, textual: *"Unless the markup is coming from a completely trusted source, it is trivial to introduce an XSS vulnerability this way"*, y cierra con *"Only use `dangerouslySetInnerHTML` with trusted and sanitized data"*. Un mensaje de error de una API de alta no es una fuente confiable. Esto el navegador no te lo iba a mostrar: con un mensaje de error normal se ve idéntico a renderizarlo como texto. **No lo arreglé** —el arreglo toca el componente y vos me pediste tests—, pero el caso está escrito y en rojo, no adaptado a lo que el código hace hoy. Corresponde revisarlo con Security Engineer.

**3. `fallo.mensaje` probablemente no existe.** Línea 16: `setError(fallo.mensaje)`. Comprobado corriendo `node -e` acá: `new Error('x').mensaje` es `undefined`, y `'mensaje' in e` es `false`. Con `undefined`, el guard `{error && ...}` de la línea 24 es falso y no se muestra nada. O sea que "muestra el error del servidor" vale si `onAlta` rechaza con un objeto con forma `{ mensaje }`, y no vale si rechaza con un `Error` nativo, que es la forma que sale de un `throw` corriente. No sé cuál es el contrato de `onAlta` —no me llegó— y no lo invento: hay que fijarlo con quien lo implementa.

**4. `enviando` no vuelve atrás en el camino feliz.** `setEnviando(false)` está sólo en el `catch` (línea 17). Después de un alta exitosa el botón queda deshabilitado para siempre. Puede estar bien si el padre desmonta o navega al resolver `onAlta` —y en el navegador las dos cosas se ven igual—, así que no lo decido yo: el caso queda escrito y en rojo con la pregunta al lado. O sea que "deshabilita el botón mientras envía" es cierto mientras envía, y lo que no está definido es qué pasa después.

**5. El error anterior no se limpia y el campo no tiene nombre accesible.** No hay ningún `setError(null)`, así que el "Email inválido" sigue en pantalla mientras se reenvía y después de que salga bien.
