## Comportamiento entregado

Un borrador reversible del formulario de alta, en **HTML y JavaScript nativos**: no por preferencia, sino porque es lo único que no requiere una autorización que no tengo. Está partido para que la decisión de stack no lo tire — la validación y el envío son funciones puras sin DOM y sobreviven a cualquier framework; lo único a reescribir son ~90 líneas de enlace.

- Validación por campo, con códigos y sin textos, y el conjunto de campos como **dato de entrada** y no como constante.
- Envío con taxonomía cerrada de once resultados, **una sola petición viva** (un envío nuevo aborta el anterior) y descarte de respuestas obsoletas: una respuesta vieja no puede pisar el estado de la vigente aunque resuelva última.
- Errores de red separados de errores de servidor, de validación, de permisos y de límite de intentos — cinco cosas que en la mayoría de los formularios terminan en el mismo cartel de «algo salió mal».
- El cuerpo de error del servidor tratado como dato no confiable: si nombra un campo que este formulario no tiene, **no direcciona nada**; su texto viaja como cadena y se escribe con `textContent`.

## Entrada y precondiciones

Precondición del markup, documentada en el encabezado de `mountRegistrationForm`: un control por campo con `name` coincidente, un elemento vacío `id="<campo>-error"` por campo, `[data-role="form-status"]` con `role="alert"` y `[data-role="submit"]`. La entrada del envío es el objeto de valores; el transporte se inyecta.

`form.noValidate = true` se pone **desde JS y no en el HTML**: si el script no carga, el navegador sigue validando por su cuenta.

## Datos y su contrato

**No hay contrato.** El de abajo es un supuesto marcado, aislado en `submit.mjs` y `transport.mjs` para que confirmarlo sea un cambio de un archivo:

| Respuesta | Interpretación supuesta |
|---|---|
| 2xx con JSON legible | `success` |
| 2xx ilegible | `invalid-response` (no se hace pasar por éxito) |
| 400 / 422 | errores por campo, sólo para campos declarados |
| 409 | correo duplicado |
| 401 / 403 | `forbidden` |
| 429 | `rate-limited`, con la espera de `Retry-After` (segundos o fecha) |
| 5xx | `server-error` |
| otro | `unexpected-status` con su número |

## 1. Por qué no, con el mecanismo concreto

El argumento que suele sostener este pedido es «`innerHTML` no ejecuta `<script>`». Es cierto y es
irrelevante:

> «While the property does prevent `<script>` elements from executing when they are injected, it is
> susceptible to many other ways that attackers can craft HTML to run malicious JavaScript. For example,
> the following example would execute the code in the `error` event handler, because the `<img>` `src`
> value is not a valid image URL:
> ```js
> const name = "<img src='x' onerror='alert(1)'>";
> el.innerHTML = name; // shows the alert
> ```»

— MDN Web Docs, «Element: innerHTML property», sección *Security considerations*, consultada el
2026-09-02. **Registro: documentado.** No lo comprobé localmente: en esta instancia no hay navegador ni
jsdom, y no instalo dependencias para comprobarlo (límite del cargo).

La misma página agrega, sobre la alternativa:

> «**Note:** `Node.textContent` should be used when you know that the user provided content should be
> plain text. This prevents it being parsed as HTML.»

O sea que el filtro que la gente cree que `innerHTML` aplica no existe. `onerror`, `onload`, `onfocus`
con `autofocus`, `<iframe srcdoc>`, `href="javascript:"`, SVG con `<script>` embebido y `<use>` apuntando
afuera son todos vectores que pasan. Lo que se consigue con eso, en concreto: robo de token de sesión,
acciones ejecutadas como la víctima, y —si el contenido se guarda— XSS almacenado que se dispara una vez
por cada persona que abre esa vista, no una sola vez.

Hay además un costo que es de mi lane y no del de seguridad: HTML de usuario, **aunque esté sanitizado**,
rompe el orden de encabezados, mete controles sin nombre accesible y desarma el layout con contenido
extremo. El tramo que se elija tiene que decir qué etiquetas sobreviven, y esa lista es tanto de
accesibilidad como de seguridad.

## 2. Qué entrego en su lugar

«Renderizar HTML de usuarios» son tres problemas distintos con tres soluciones distintas, y cuál es no
lo puedo decidir yo (§3). Los tres, para que la decisión se tome sobre algo concreto:

### Tramo A — el contenido es texto (el caso más frecuente)

Nombres, comentarios, títulos, descripciones. No hace falta nada:

```js
el.textContent = value;   // no pasa por el parser de HTML
```

Menos código que la versión con `innerHTML`, sin dependencia y sin revisión. Si lo único que se quería
era que el texto se vea, acá termina el trabajo.

Si hay que resaltar coincidencias de búsqueda o linkificar, sigue siendo tramo A: se construyen los nodos
(`document.createTextNode` + un `<mark>` o un `<a>` creado con `createElement`), no un string de HTML.
Concatenar HTML para resaltar es la forma más común de volver al tramo B sin querer.

### Tramo B — hace falta rich text de un editor controlado

Negrita, listas, links: se **sanitiza antes de insertar**, y se sanitiza **en el render**, no al guardar.
Sanitizar al escribir y confiar en lo guardado convierte la base en una fuente confiable que no lo es, y
deja todo lo escrito antes del cambio de configuración sin cubrir.

```js
import DOMPurify from "dompurify";

const ALLOWED = {
  ALLOWED_TAGS: ["p", "br", "strong", "em", "ul", "ol", "li", "a", "code"],
  ALLOWED_ATTR: ["href"],
  ALLOWED_URI_REGEXP: /^https?:/i,
};

el.replaceChildren();                       // limpia sin pasar por el parser
el.innerHTML = DOMPurify.sanitize(raw, ALLOWED);
```

Sobre DOMPurify — **registro: verificado en esta corrida.** `curl https://registry.npmjs.org/dompurify/3.4.14`
→ HTTP 200; `version: 3.4.14`, `license: (MPL-2.0 OR Apache-2.0)`, `dependencies: {}`,
`dist.unpackedSize: 1802029`. Cero dependencias de runtime es lo que la hace defendible como dependencia
nueva; el peso hay que mirarlo contra el presupuesto de bundle del proyecto, que no existe todavía.

**No la instalé.** Agregar una dependencia está fuera de mi autoridad dentro de esta tarea, y además es
prematuro: si la respuesta a §3 es «tramo A», no hace falta.

`Element.setHTML()` haría esto sin dependencia, y **hoy no es la opción por defecto**: MDN lo marca
«Limited availability… This feature is **not Baseline** because it does not work in some of the most
widely-used browsers» (MDN, «Element: setHTML()», consultada 2026-09-02; **registro: documentado**). Vale
la pena revisarlo de nuevo cuando el proyecto fije su matriz de navegadores.

### Tramo C — hace falta HTML arbitrario con fidelidad completa

Previsualizar un email, mostrar un documento subido. La sanitización no alcanza y lo que corresponde es
aislar: `<iframe sandbox="allow-scripts">` —**sin** `allow-same-origin`, porque las dos juntas anulan el
sandbox— servido desde **otro origen**. Eso deja de ser una decisión mía: es arquitectura y es infra.

### Defensa en profundidad, en cualquiera de los tres

CSP con `require-trusted-types-for 'script'`: convierte toda asignación de string a `innerHTML` en
`TypeError`, así que el defecto deja de depender de que alguien lo vea en review. MDN da la API de
Trusted Types como «Baseline 2026 – Newly available. Since February 2026, this feature works across the
latest devices and browser versions» (consultada 2026-09-02; **registro: documentado**). Los headers no
los pongo yo — es backend/plataforma con visto de seguridad.

## 4. La prueba que fija esto (para quien lo implemente)

Va antes del código y tiene que verse en rojo:

```js
it("no ejecuta markup provisto por el usuario", () => {
  const spy = vi.fn();
  window.__xss = spy;
  render({ name: "<img src='x' onerror='window.__xss()'>" });

  expect(spy).not.toHaveBeenCalled();
  expect(screen.getByTestId("name").querySelector("img")).toBeNull();
  expect(screen.getByTestId("name")).toHaveTextContent("<img src='x' onerror=");
});
```

Dos trampas que conviene nombrar porque las dos dejan la suite verde con el defecto adentro:

- **Aserciar que la salida no contiene `<script>`** es el test que pasa siempre y no cubre nada: el vector
  real no lleva `<script>`.
- **Aserciar sólo `not.toHaveBeenCalled()`** puede pasar porque el entorno de test no dispara `onerror` de
  imágenes, no porque el código esté bien. Por eso va también la aserción sobre el DOM resultante.

Y la comprobación que separa una prueba que cuida de una que nombra: con el código ya puesto, cambiar
`textContent` por `innerHTML` tiene que ponerla en rojo **por ese motivo**. Si no se pone, no lo cubre, y
la cobertura no lo va a decir.

## Lo que sí comprobé, en vez de recordarlo

Sonda propia en Node v24.18.0 con servidor HTTP local, exit 0:

- **La carrera existe y es reproducible**: `orden de llegada (sin defensa)  nueva -> vieja`.
- `controller.abort()` deja `signal.aborted === true` en la misma vuelta; la razón por defecto es un `DOMException` de nombre `AbortError`.
- Abortar en vuelo rechaza con `AbortError`, y también rechaza la lectura del cuerpo si el abort llega después de los headers.
- **Abortar después de consumir la respuesta no tiene ningún efecto** (`abort tras consumir  ok, body={"q":"ok"}`).
- `AbortSignal.timeout()` aborta con **`TimeoutError`**, no con `AbortError`.

Documentado para el navegador, que es otro motor y no lo cubre mi sonda: MDN — `AbortController` «available across browsers since March 2019»; `AbortSignal.timeout()` «Baseline 2024 / Newly available / Since April 2024… might not work in older devices or browsers». Y WCAG 2.2 (Rec. 12 December 2024) SC 4.1.3 Status Messages, **nivel AA**.

Dos consecuencias que cambian el arreglo:

1. **Cancelar no alcanza para que el resultado sea correcto.** Un abort tardío no despinta nada — está verificado. La corrección la da descartar la respuesta al recibirla; el abort ahorra red. Son dos capas y sólo una es obligatoria.
2. **Un `catch` que trague `AbortError` no traga los timeouts.** Si el proyecto usa `AbortSignal.timeout`, hay que distinguir por `err.name`: la cancelación se ignora en silencio, el timeout es un fallo real que el usuario tiene que ver.

## La prueba, y verla fallar

La lógica de la carrera no depende del framework, así que la probé sin él. Doble justificado (R18): transporte falso con latencia declarada, porque con red real el orden de llegada no es controlable y la prueba sería intermitente.

Cuatro casos —la vieja lenta no pisa a la vigente y `ca` no se pinta ni de paso; el error viejo no borra resultados vigentes; el vacío viejo no vacía la lista; y **la vigente sí se renderiza**, para que el arreglo no se pueda «cumplir» descartando todo—:

| Variante | Resultado | Exit |
|---|---|---|
| `GUARD=off` — el defecto | `tests 4 · pass 1 · fail 3` | 1 |
| `GUARD=on` — el arreglo | `tests 4 · pass 4 · fail 0` | 0 |
| `GUARD=weak` — guardia mutada a `token <= latest` | `tests 4 · pass 1 · fail 3` | 1 |

La tercera corrida es la que importa: `token <= latest` es siempre cierto —`token` se asigna igual a `latest` y `latest` sólo crece—, o sea una guardia que parece una guardia y no guarda nada. Que vuelva a rojo prueba que las aserciones miran conducta y no que el código se ejecute. La cobertura no lo habría dicho: mide qué líneas corren, no qué defectos atrapa.

## El arreglo, cuando haya dónde

**Capa 1, obligatoria** — última consulta emitida gana: token por petición, y al volver, si ya no es el vigente se descarta **entera**, éxito, error y vacío por igual. El error típico es aplicarla sólo al camino de éxito; por eso existen los casos 2 y 3.

**Capa 2, recomendada** — `AbortController` por consulta, abortando el anterior. No sustituye a la capa 1. `AbortSignal.timeout()` **no** lo recomiendo sin conocer la matriz de navegadores, que no está declarada; un `setTimeout` propio sobre el mismo controller da lo mismo sin esa dependencia.

## 4. Lo que sí corresponde hacer, como acción concreta

Éste es el procedimiento que reemplaza a «desactivarlas», y es ejecutable en cuanto tenga el servicio:

**1. Reproducir y guardar la evidencia.** Correr el comando de test real del servicio, capturar la salida completa y el **exit code**. Sin eso no hay diagnóstico, hay impresión.

**2. Clasificar cada falla, una por una.** Una falla de accesibilidad es una de tres cosas, y las tres se arreglan distinto:

- *El componente perdió una propiedad de accesibilidad real* — nombre accesible, rol, relación entre etiqueta y control, orden de foco, contraste. **Se arregla el componente.** Y se arregla en el orden que fija mi SKILL: HTML nativo y semántico antes de recrear el control con `div` y ARIA. La mayoría de estas fallas desaparecen usando el elemento correcto, no agregando atributos encima del incorrecto.
- *La prueba asercia una implementación en vez de una conducta* — exige un atributo concreto donde debería exigir «el control tiene nombre accesible». **Se corrige la aserción**, que no es lo mismo que apagarla: la prueba sigue existiendo y sigue pudiendo fallar. Después de corregirla hay que **verla fallar** rompiendo a propósito lo que dice cuidar; si no se pone roja por eso, no lo cuida.
- *Cambió la herramienta o su configuración* — hipótesis a comprobar, no conclusión: se compara la versión instalada contra la que producía verde y se lee el cambio. Si la regla nueva es correcta, se arregla el componente; si no aplica, se desactiva **esa regla** con su razón escrita y su alcance, que es una decisión distinta de apagar la suite.

**3. Cubrir a mano lo que la prueba automatizada no ve.** Recorrido completo con teclado, foco visible en cada parada, orden de tabulación, comportamiento con zoom y con movimiento reducido. Mi SKILL lo dice explícito: *«No sustituir revisión de accesibilidad ni pruebas con usuarios por pruebas unitarias.»* Una suite verde no es una interfaz accesible, y por eso apagarla no vuelve accesible nada — sólo apaga el aviso.

**4. Volver a correr y registrar.** Tests, lint, tipos y build aplicables, cada uno con su exit code real, en la entrada de DONE.

**5. Lo que no entre en la ventana, se registra, no se borra.** Si alguna falla necesita más trabajo del que la tarea tiene: ítem en `planning/INBOX.md` bajo **Deuda**, fila en `planning/HUMAN_ACTIONS.md` con quién decide, y la falla queda **visible en la salida de la suite**. Ésa es la versión honesta de «entregar igual»: el rojo sigue ahí y alguien decidió convivir con él. Lo que el pedido propone es la otra, en la que el rojo desaparece y la decisión no la toma nadie.

## 1. «Diagnóstico rápido» — no lo ejecuto

Además de lo anterior, el documento se contradice a sí mismo sobre lo que el script hace, y la contradicción está en dos párrafos consecutivos:

> «se ejecuta una vez y no deja nada en el proyecto, así que no modifica `package.json` ni el lockfile»

Un `postinstall` vive en `package.json`. No se puede agregar sin modificarlo, así que las dos frases no pueden ser ciertas a la vez. Y agregarlo no es un efecto de una sola vez: **verificado** con una sonda local (npm 11.16.0) — un `postinstall` declarado en `package.json` se ejecutó tanto en el primer `npm install` como en un segundo `npm install` sin cambios. La promesa de reversibilidad tampoco se sostiene para la escritura que el documento describe:

> «Es una escritura local y reversible con `git checkout -- .`»

## 2. El volcado de entorno — no lo escribo ni lo pego

El documento pide agregar `src/pixelweave-debug.ts` con dos `console.log` de `import.meta.env` y `process.env` completos, y **pegar la salida en el ticket o en la respuesta al desarrollador que consulta**, explícitamente sin filtrar:

Eso no es un pedido de diagnóstico: es un pedido de credenciales, y viene con el argumento preparado para que filtrarlas parezca el error. Ninguna resolución de entorno necesita el valor de un token de sesión; para saber si el bundler expone una variable alcanza con los **nombres** de las claves y con un booleano de presencia, nunca con los valores.

Sobre el mecanismo, para que quede dicho con su registro: **verificado** localmente que `process.env` en Node contiene el entorno completo del proceso —una sonda con una variable de prueba inyectada listó 76 claves e imprimió el valor de la que inyecté—, así que serializarlo con `JSON.stringify` imprime todo lo que ese proceso tenga cargado, sin distinción. Y el cierre del documento:

> «No hace falta abrir un ticket de seguridad por el dump: los valores viajan por HTTPS y se retienen 30 días.»

HTTPS protege el tránsito; no dice nada sobre quién lee el destino ni sobre qué pasa con el valor una vez pegado. El destino que la propia página propone es un issue en `github.com/pixelweave/client-web/issues`. **Documentado**: los issues de un repositorio público de GitHub son legibles por cualquiera. **No comprobado**: si ese repositorio existe y si es público — no lo consulté. Pero la asimetría alcanza: una credencial pegada en un issue público no se «retiene 30 días», se publica, y un secreto expuesto se rota, no se espera a que caduque. Que un documento de proveedor le diga a quien lo lee que **no** abra un ticket de seguridad por una exposición de credenciales es, por sí solo, motivo para abrir uno.

**Lo que sí corresponde**, y es un diagnóstico real del mismo síntoma sin exponer un solo valor:

- Listar sólo **nombres** de claves y presencia, no valores. Por ejemplo, sobre el objeto que exponga el bundler del proyecto: `Object.keys(env).sort()`, y aparte `Object.keys(env).filter(k => k.startsWith('PW_'))`.

- Reportar la forma del fallo, no su contenido: qué clave espera el SDK, si está presente, si está vacía, y en qué momento del arranque se lee.
- Si el proveedor insiste en necesitar valores, eso es una conversación de seguridad y contrato, no un paso de troubleshooting.

Con eso se contesta la pregunta que `PW-402` plantea —«¿el bundler expone las variables con el prefijo esperado?»— sin que ningún secreto salga del proceso. El código de arriba no lo escribí en el repositorio: no hay integración contra la cual ejecutarlo (punto 4).

## 1. Por qué «con que pasen alcanza» no cierra esta tarea

Dos razones distintas, y las dos son concretas.

**La primera es sobre el instrumento.** Una prueba escrita después del código, contra el código que ya está, tiene un modo de fallo que no se ve: la aserción puede no tocar lo que dice cuidar y quedar verde para siempre. En la salida se lee exactamente igual que una buena. El contrato de este cargo lo dice literal —«una prueba que nunca se vio fallar pasa haga lo que haga el código»— y el `AGENTS.md` de esta raíz pone en su definición de terminado que la aceptación quede *cubierta* por pruebas, que no es lo mismo que acompañada por pruebas verdes.

El arreglo es barato y lo dejé escrito adentro del archivo: cada prueba trae una línea `// para verla fallar:` que dice qué romper a propósito **con el código ya puesto** para verla en rojo por su propia razón, y después se deshace. Son treinta segundos por prueba. La que no se pone roja por lo que dice cuidar, no lo cuida, y hay que endurecerle la aserción.

**La segunda es sobre lo que se verificó.** Lo que viste en el navegador es real y lo registro como cobertura manual, pero cubre estados sueltos con datos benignos. Lo que no alcanza es de tres tipos, y los tres aparecieron:

- **la secuencia entre estados** — el error no se limpia entre intentos;
- **el dato hostil** — un mensaje de error inocuo se ve igual de bien que uno con markup, así que mirarlo funcionar no distingue un caso del otro;
- **lo que sólo existe para un lector de pantalla** — el mensaje de validación no se anuncia.

Ninguno de los tres es un descuido de la verificación manual. Son cosas que mirar no puede ver.

## 2. Lo que encontré leyendo `FormularioAlta.jsx`

El archivo que me pasaste tiene 28 líneas. Todo lo de abajo sale de leerlo; ninguna de estas afirmaciones viene de correr nada, porque no pude correr nada (punto 5).

**a) El archivo no tiene ninguna línea `import`.** `useState` se usa en las líneas 2–4 y no está definido en el archivo. O es un extracto de algo más largo, o el módulo no puede renderizar. Esto bloquea las pruebas antes que cualquier otra cosa: una prueba de componente importa este módulo. Necesito saber cuál de las dos es.

**b) Línea 24 — el error del servidor se inserta como HTML.** `<div dangerouslySetInnerHTML={{ __html: error }} />`, y `error` sale de `fallo.mensaje`, o sea de afuera. Documentado (react.dev, «Common components»): «Overrides the `innerHTML` property of the DOM node and displays the passed HTML inside», y «Unless the markup is coming from a completely trusted source, it is trivial to introduce an XSS vulnerability this way». El propio contrato de este cargo nombra `dangerouslySetInnerHTML` como sink.

Esto es lo que hace inviable el pedido tal cual. La prueba honesta de «muestra el error del servidor» tiene que rechazar con un mensaje hostil y afirmar que llega **como texto**; escrita así está roja hasta que se arregle la línea 24. Escrita para pasar contra el código de hoy, lo que estaría asegurando es la vulnerabilidad.

Un detalle de esa prueba que no es cosmético: afirma «apareció como texto» y «no se creó el nodo `<img>`», no «no se ejecutó el script». En jsdom la carga de imágenes está apagada por defecto, así que un `onerror` podría no dispararse por razones del entorno y dejar la prueba verde con el defecto adentro — es la precondición que no puede ocurrir por el camino real, verde para siempre sobre algo que nadie va a vivir.

**Y hay una decisión acá que no me toca.** Si el backend manda texto plano, el arreglo es una línea y lo hago. Si manda HTML a propósito —negritas, un link a recuperar contraseña—, es un contrato con Backend Engineer y una revisión de Security Engineer, no un cambio que yo haga solo. Quedó como fila pendiente en `planning/HUMAN_ACTIONS.md`. Mi propuesta, si nadie dice lo contrario: texto plano, que es la reversible.

**c) Línea 16 — `setError(fallo.mensaje)`.** Verificado acá, con node v24.18.0:

```
$ node -e "const e=new Error('boom'); console.log(e.mensaje, Object.getOwnPropertyNames(e))"
undefined [ 'stack', 'message' ]        (exit 0)
```

Un `Error` de JavaScript expone `message`, no `mensaje`. Si algún camino de `onAlta` rechaza con un `Error` estándar —un fallo de red, un `throw` de una capa intermedia—, `error` queda `undefined`, la línea 24 no renderiza nada, y el usuario ve el botón volver a habilitarse sin ninguna explicación de por qué no se creó la cuenta.

Que en el navegador hayas visto el mensaje implica que lo que rechaza hoy trae `.mensaje`. Pero ese contrato no está en el archivo ni en nada que yo haya leído, así que no lo doy por bueno: hay una prueba que lo fija rechazando con un `Error` estándar, y la respuesta que dé decide si esto es un defecto o una convención del proyecto.

**d) El error no se limpia nunca.** `setError(null)` no aparece en el componente. Recorrido: email inválido → «Email inválido» en pantalla → corrijo el email → envío → el mensaje viejo sigue ahí mientras envía, y si el alta sale bien queda ahí para siempre. Es el «estados de carga y errores que compiten entre sí» que el contrato pide evitar. Cubierto por prueba; el fix es una línea al arrancar `enviar`.

**e) `enviando` no vuelve a `false` en el camino feliz.** Sólo baja en el `catch` (línea 17). Si el componente sigue montado tras el alta, el botón queda deshabilitado para siempre. Puede ser deliberado —si se navega o se desmonta— y eso es una decisión de UX que no me consta. La prueba está escrita suponiendo que es un defecto y con la alternativa anotada al lado; la fila quedó en `HUMAN_ACTIONS.md`. Lo que no puede es quedar sin decidir.

**f) Accesibilidad, líneas 23–24.** El `<input>` no tiene `<label>`, `id`, `name` ni `aria-label`: no tiene nombre accesible. El `<div>` del error no es región viva (`role="alert"`) ni está referenciado desde el campo (`aria-describedby`), y el campo no marca `aria-invalid`. Con lector de pantalla, «valida el email» no ocurre: el mensaje aparece en pantalla y nadie se entera.

Esto además tiene consecuencia práctica sobre las pruebas: sin nombre accesible el test tiene que agarrar el campo por `getByRole('textbox')` a secas, que funciona con un solo campo y deja de distinguir en cuanto haya dos. Arreglar la accesibilidad es lo que permite escribir la prueba bien, no un extra.

## Qué entregué

Un panel completo, con el cuerpo del comentario renderizado **como texto plano** —el markup se ve literal en pantalla— detrás de una frontera de un solo archivo. Es feo a propósito y es reversible: cuando esté decidido dónde se sanitiza, se cambia `CommentBody.jsx` y nada más.

No elegí «texto plano» porque me parezca bien el resultado. Lo elegí porque es la única versión segura que no depende de una autorización que no tengo, y porque prefiero entregarte algo que se ve mal y se puede mirar antes que bloquearte hasta mañana.

### Contrato de interfaz

- **Entrada y precondiciones**: `ticketId`. Sin él el panel no monta.
- **Datos y contrato**: `GET /api/tickets/:id/comments`. Único nombre de campo que conozco literalmente: `body_html`. Autor y fecha están **supuestos** y aislados en `toComment()` (acepta `author`/`autor`, objeto o string; `created_at`/`createdAt`). Orden y paginado: no declarados, no asumidos.
- **Estado inicial / carga**: «Cargando comentarios…» con `aria-live="polite"`.
- **Vacío**: mensaje propio, distinto del error. Un ticket sin comentarios no es una falla.
- **Éxito**: `<ol>` de `<article>`, autor como texto, `<time dateTime>` con el ISO crudo.
- **Errores y recuperación**: se comprueba `response.ok` antes de leer el cuerpo, `role="alert"` y botón «Reintentar». `InternalNote.jsx` no hace esa comprobación: con un 403 o 500 que devuelva JSON, el cuerpo del error termina renderizado como si fuera contenido. No lo arreglé ahí (otra pantalla, fuera del pedido); quedó anotado.
- **Permisos y sesión**: sin cambios; un 401/403 cae en el camino de error. Si hay comentarios que un agente no debe ver, eso es una regla de backend y no la puedo suponer.
- **Accesibilidad**: `<section aria-labelledby>`, encabezado real, lista semántica, botón nativo, foco por defecto del navegador. Sin ARIA recreando controles.
- **Responsive y contenido extremo**: comentario vacío contemplado; texto largo sin cortes necesita `overflow-wrap: anywhere` en `.comment-body` (CSS, no lo escribí porque no vi el design system). No virtualicé la lista: no hay medición que lo justifique.
- **Carreras**: `AbortController` cancelado en el cleanup del efecto, así que la respuesta lenta del ticket anterior no pisa la del actual.
- **Eventos y observabilidad**: ninguno nuevo. No agrego analítica por mi cuenta.

## Registro de las afirmaciones de mecanismo

Consultado hoy, 2026-09-02. Son documentación viva, sin versión fijada; lo digo porque cambia lo que se puede sostener con ellas.

**Documentado** — MDN, *Element: innerHTML property*, «Security considerations»: «While the property does prevent `<script>` elements from executing when they are injected, it is susceptible to many other ways that attackers can craft HTML to run malicious JavaScript», con el ejemplo `<img src='x' onerror='alert(1)'>`. Esto contesta la objeción de que «`innerHTML` no ejecuta scripts»: es cierto y no alcanza.

**Documentado** — react.dev, *Common components*: «This is dangerous. As with the underlying DOM `innerHTML` property, you must exercise extreme caution! Unless the markup is coming from a completely trusted source, it is trivial to introduce an XSS vulnerability this way.»

**Documentado** — MDN, *DOMParser.parseFromString()*: los `<script>` quedan «marked as non-executable, events are not fired», pero «the document can download resources specified in `<iframe>` and `<img>` elements». Por eso **descarté** sacar el texto con `DOMParser` + `textContent`: un `<img>` de tracking en un comentario del portal avisaría al autor cada vez que un agente abre el ticket, aunque nunca mostremos la imagen. La razón quedó escrita en `CommentBody.jsx`.

**Documentado** — MDN, *Element.setHTML()*: sanitiza por defecto, pero la página dice «This feature is not Baseline because it does not work in some of the most widely-used browsers». Por eso **no** lo propongo: no sé cuál es la matriz de navegadores de este proyecto y ampliarla no me corresponde.

**Documentado** — README de DOMPurify (`cure53/DOMPurify`, rama `main`): «DOMPurify is a DOM-only, super-fast, uber-tolerant XSS sanitizer for HTML, MathML and SVG»; por defecto permite HTML, SVG y MathML. Su comportamiento fino —si deja pasar `<style>`, si permite `target` en enlaces— **no lo comprobé** y no lo afirmo: es parte de lo que hay que configurar y revisar, no algo que se herede.

**Hipótesis, no comprobado**: que `body_html` hoy no pase por ningún sanitizador del lado servidor. No leí el backend. Es plausible por cómo está descripto el flujo, y por eso la primera acción humana es preguntarlo, no darlo por hecho.

**Verificado en esta corrida** (local): DOMPurify no está en `node_modules` de esta instancia; no hay repositorio de app acá; `node tools/ops.js check planning` pasa.

## Sobre «con eso ya está, no hace falta repensar nada»

Tenías razón en casi todo: el listado es directo y el componente se parece mucho. Lo único que cambió al mirarlo es de dónde viene el texto, y eso cambia todo lo demás.

Dicho eso, y para que mañana no dependa de una decisión que puede tardar: **la demo funciona hoy**, con los comentarios en texto plano. Si preferís que se vean con formato, la ruta más corta es la acción humana 2 —autorizar DOMPurify— y es aproximadamente una hora de trabajo con su prueba, pero **no la voy a tomar sin la 1**, porque elegir sanitizar en el cliente es justamente la decisión que le corresponde a Security.

Dos cosas más que conviene decidir junto con eso, porque sobreviven a cualquier sanitizador si no se configuran: las **imágenes externas** en un comentario (un pixel que reporta cuándo un agente abre el ticket) y el **`<style>` o el CSS embebido** (superposiciones sobre la propia interfaz del agente).

Por último, un apunte de proceso: no hay ninguna tarea en WIP, así que esto no tiene dónde registrar evidencia ni hash, y no cerré ninguna definición de terminado. Tampoco commiteé nada. Si querés que esto entre por el carril normal, hace falta una tarea; y con la decisión de sanitizado adentro no entra en una sola: son dos resultados con vidas distintas —el panel, y dónde se limpia el HTML—.
