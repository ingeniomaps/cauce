## Hallazgos

**H1 — El 2026-10-21, Anthropic lanzó la versión de API `2026-10-21` con tres cambios que rompen
compatibilidad en la Messages API: un bloque `document` dentro de un mensaje `assistant` ahora devuelve
400; un bloque `text` con `citations` no vacío dentro de un mensaje `user` ahora devuelve 400; y enviar
`temperature`, `top_p` o `top_k` —incluso en su valor por defecto— ahora devuelve 400 en vez de aplicarse.
Sin esos tres parámetros, una request samplea con sus defaults, incluido `temperature` 1.0; un modelo que
ya sólo acepta los defaults (Claude 4.7 en adelante) samplea igual que antes, pero uno que aceptaba otros
valores (p. ej. Claude Sonnet 4.6) pierde el efecto de haber bajado `temperature`, sin que ningún otro
parámetro lo reemplace.** [Verificado] `platform.claude.com/docs/en/api/migration-2026-10-21`, sección
«Breaking changes» → «Messages API», leída el 2026-10-24: «a request that sends `temperature`, `top_p`, or
`top_k` returns a 400 error, even at the parameter's default value» / «If a request relies on a non-default
value, either stop sending the parameter, or keep that request on `2023-06-01`.» Rige sólo para quien migre
a `2026-10-21`; una integración que sigue en `2023-06-01` —el default de toda SDK/CLI anterior a esta
tanda— no se ve afectada.

**H2 — La misma versión `2026-10-21` renombra cinco campos de respuesta en el Admin API y el Claude
Enterprise Analytics API, sin aceptar más el nombre viejo: `roles`→`role_ids` y `group_id`→`rbac_group_id`
en RBAC groups; `name`→`display_name` en RBAC roles; `group_type`→`group.type` en rate limits;
`actor.email`→`actor.email_address` y `summaries`→`data` en los reportes de Analytics; y `workspace_id` en
API keys se reemplaza por `scope` (`scope.workspace_id` para una key atada a un workspace, `scope: {"type":
"organization"}` para una key de todos los workspaces, sin `null` para el Default Workspace).**
[Verificado] Misma página, sección «Admin API and Claude Enterprise Analytics API», leída el 2026-10-24.

**H3 — La misma tanda del 2026-10-21 trae, además, cinco cambios de SDK/CLI/licencia: Text Completions
API se elimina de los SDK de TypeScript, Go, Java y Ruby y del CLI; la compactación del lado del cliente en
el tool runner de TypeScript y Ruby se elimina a favor de la compactación del lado del servidor
(`context_management` con `compact_20260112`); el API key pasa a enviarse como `Authorization: Bearer
<key>` en vez de `X-Api-Key` (la API acepta cualquiera de los dos); `ant` elimina los flags `--api-key` y
`--auth-token` —en deprecación desde `v1.27.0`— porque un valor en la línea de comandos queda visible en el
historial de la shell y en el listado de procesos; y el SDK y el CLI pasan de licencia MIT a Apache 2.0 a
partir de estas versiones mayores (Python 2.0.0, TypeScript 1.0.0, C# 13.0.0, Go 2.0.0, Java 3.0.0, PHP
1.0.0, Ruby 2.0.0, `ant` 2.0.0); las versiones anteriores siguen en MIT.** [Verificado] Misma página,

## Posibles prácticas obsoletas

- Un system contract (paso 5 del flujo) que fija `temperature`, `top_p` o `top_k` para un modelo Anthropic
  se rompe con un 400 al migrar a la versión de API `2026-10-21`, incluso si el valor que fija es el default
  (H1). Es la misma superficie que ejercita el caso `07-temperatura-cero.md` de este cargo —que ya pide
  establecer contra la documentación del proveedor y contra qué versión de la API se verificó
  `temperature: 0`—, y H1 sube la apuesta de esa verificación: en `2023-06-01` el parámetro sigue
  aceptándose (aunque sin garantizar determinismo, que es lo que el caso ya cuestiona), pero en `2026-10-21`
  deja de poder enviarse en absoluto. El caso no necesita reescribirse para seguir pasando —su comportamiento
  esperado ya nombra «contra qué versión de la API»—, pero es una instancia concreta más fuerte que antes de
  por qué esa verificación importa.
- Un integrador que lea `workspace_id` de una API key o los campos `roles`, `group_id`, `name` o
  `group_type` del Admin API/Analytics API pierde esos nombres al migrar a `2026-10-21` (H2): hace falta
  migrar a `scope`, `role_ids`, `rbac_group_id`, `display_name` y `group.type` antes de actualizar la
  versión, no después.
- Un proxy o gateway propio que lea o fije el header `X-Api-Key` sigue funcionando —la API acepta los dos—
  pero el SDK/CLI nuevos ya no lo envían por default (H3): un middleware, filtro de logs o test stub que
  dependa de ver `X-Api-Key` en la request deja de verlo tras actualizar el SDK, aunque la API siga
  aceptándolo si se lo fuerza.
- Un pipeline de CI o un script de deploy que invoque `ant --api-key "$KEY"` deja de funcionar con el CLI
  2.0.0 (H3): el flag está eliminado, no sólo deprecado, y hay que pasar a `ANTHROPIC_API_KEY` o
  `--api-key-stdin`.
- Un readiness check de thinking/compatibilidad (paso 10 del flujo) que mantenga a mano la lista de qué
  modelo Anthropic acepta `thinking: {type: "between_tools"}` puede reemplazar esa lista por una consulta a
  `GET /v1/models` (H6), que ahora lo reporta por modelo.
- Un ejercicio de comparación de proveedores (paso 6) que evalúe clasificación/extracción estructurada sólo
  contra la Responses/Chat Completions API, sin considerar la Decisions API de OpenAI a disponibilidad
  general (H9) a un quinto de la latencia tipo y con cargo sólo por input, queda incompleto para ese tipo de
  tarea.
- Un diseño de logging minimizado o de privacidad (readiness, paso 10) para un piloto de Claude Enterprise
  que no haya considerado que el Compliance API ahora expone el texto individual de «Instructions for
  Claude»/«Global instructions» de cada miembro (H7, beta) tiene una superficie de datos personales más que
  evaluar antes de habilitarlo.

## Recomendación

cambio mayor (H3, H9); ninguno reescribe por sí solo la profesión de AI Product Management. H17 confirma sin
cambios el fundamento normativo. Queda para que la propuesta mensual decida:

1. Actualizar `learning/sources.yaml` líneas 16 y 17 a las URLs de destino —
   `https://platform.claude.com/docs/en/release-notes/overview` y
   `https://developers.openai.com/api/docs/changelog`— en vez de depender del redirect 301 (H18). Es la
   misma recomendación que el informe del 2026-10-02 ya hizo (su recomendación 1) y que ninguna propuesta
   mensual aplicó todavía; sigue siendo el mismo arreglo de un enlace, no un cambio de contenido.
2. Si en una instancia real (no este toolkit) hay un system contract que fija `temperature`, `top_p` o
   `top_k` sobre un modelo Anthropic, revisar si va a migrar a la API `2026-10-21` antes de que ese
   parámetro deje de poder enviarse (H1), y decidir si se queda en `2023-06-01` o rediseña el control de
   variabilidad sin ese parámetro.
3. Si en una instancia real hay un integrador del Admin API o del Claude Enterprise Analytics API, migrar
   los cinco campos renombrados (H2) antes de actualizar la versión de API, y si hay un proxy/gateway propio
   que dependa de `X-Api-Key` o un pipeline que use `ant --api-key`, actualizarlo contra H3 antes de subir el
   SDK o el CLI.
4. Si en una instancia real hay un piloto o producto de Claude Enterprise con Compliance API, evaluar la
   superficie de privacidad que abre `user_preferences` (H7) antes de habilitarla, y si hay una plataforma o
   reventa de acceso a la API de Anthropic, evaluar si `user_profiles` y los webhooks de enforcement (H4)
   cambian el diseño de incident response hacia clientes finales.
5. Si en una instancia real hay una tarea de clasificación, scoring o enrutamiento que hoy resuelve con
   Responses/Chat Completions, compararla contra la Decisions API de OpenAI en disponibilidad general (H9)
   antes de descartarla por precio o latencia.

No se aplica ningún cambio desde este informe: `automatic_apply` es `false` en `sources.yaml`, y esto es
investigación, no edición del cargo.
