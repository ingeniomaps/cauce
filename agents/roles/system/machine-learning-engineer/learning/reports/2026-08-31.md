## Hallazgos

### H1 — NIST AI RMF 1.0 sigue sin contenido revisado desde 2023-01-26; la página del programa confirma que la revisión sigue en curso, sin cronograma en la fuente primaria

Confianza: **alta** para lo verificado; el resto queda en «Preguntas abiertas».

La página de publicación (verificado) da fecha de publicación **2023-01-26**, sin nota de revisión posterior
ni de una versión 1.1. La página del programa (`nist.gov/itl/ai-risk-management-framework`, verificado, cita
literal) dice: **«The AI RMF 1.0 is being revised as part of the White House AI Action Plan»**, y la página de
«Engage» del mismo programa (verificado) repite la misma frase sin agregar cronograma ni detalle de contenido.
Esto confirma sin cambios lo que `references/operating-model.md` ya registra («NIST indica que está en
revisión»): sigue siendo así, con una fuente primaria adicional que lo sostiene.

Una búsqueda web (no primaria) devolvió afirmaciones más específicas —que la revisión eliminaría referencias
a *misinformation*, DEI y *climate change*, y que una revisión formal con participación de la comunidad no
se espera antes de 2028— que **no pude confirmar** en ninguna de las tres páginas primarias de NIST
consultadas, ni en el PDF del AI Action Plan (que esta corrida no pudo leer como texto: ver «Evidencia»).
Quedan en «Preguntas abiertas» como hipótesis, no como hallazgo.

### H2 — Nuevo desarrollo: NIST abrió un perfil sectorial para infraestructura crítica, hoy en fase de concept note sin borrador publicado

Confianza: **alta**.

`nist.gov/programs-projects/concept-note-ai-rmf-profile-trustworthy-ai-critical-infrastructure` (verificado)
da: título «Concept Note: AI RMF Profile on Trustworthy AI in Critical Infrastructure», creado **2026-04-06**
y actualizado **2026-07-17**, estado **«Ongoing»**. Alcance declarado: energía, salud, transporte y
manufactura, cubriendo IT, tecnología operacional y sistemas de control industrial; NIST formó una
«Community of Interest» para recibir borradores de discusión. No hay borrador de perfil publicado a la fecha
de esta corrida (2026-08-31).

Impacto ML: ninguno de los cinco documentos que `operating-model.md` cita como fundamento externo cubre hoy
un perfil específico para infraestructura crítica. No corresponde citarlo todavía en `sources.yaml` —es una
nota conceptual, no una norma publicada—, pero vale como candidato a vigilar para cualquier sistema de ML que
opere sobre esos sectores (energía, salud, transporte, manufactura).

### H4 — PyTorch: última release 2.13.0 (2026-07-08); el resumen automático de la página HTML de releases le puso 2024

Confianza: **alta** para versión y fecha (contrastada por dos vías independientes); **alta** para el
contenido de los breaking changes, citados literalmente de las notas de la release.

La API de releases de GitHub (verificado, JSON crudo) da `tag_name: "v2.13.0"`, `published_at` **8 de julio de
2026**. Las notas de la release (verificado, `github.com/pytorch/pytorch/releases/tag/v2.13.0`, cita literal)
listan como cambios incompatibles: remoción de binarios CPython 3.13t (free-threaded), remoción total del
soporte de build con Bazel, remoción completa de named tensors, `PyObject` desnudo ya no permitido en schemas
de operadores, rediseño de copy-on-write en `StorageImpl` (pierde `is_cow()`/`maybe_materialize_cow()`),
cambio de `shared_ptr` a `intrusive_ptr` para `Tensor.grad_fn` en autograd de C++, mínimo de NCCL elevado a
2.23, y `onednn::qconv2d_pointwise` deja de mutar buffers de entrada in-place. Ninguno de estos cambios toca
directamente las prácticas que `SKILL.md`/`operating-model.md` de este cargo nombran (splits, leakage,
métricas, evaluación GenAI): son de infraestructura de build, C++ y distribución.

Nota de método: la primera consulta a este mismo dato —`github.com/pytorch/pytorch/releases` en HTML, vía
fetch con resumen automático— devolvió **«Release Date: July 8, 2024»** para la misma versión 2.13.0. La API
JSON, consultada por separado, da **2026**, y coincide con la fecha que muestra la página de la release
específica. Es el mismo tipo de error que documentó `qa-engineer` el 2026-08-29 (año errado en un resumen de
HTML de GitHub Releases, contradicho por la API JSON del mismo repositorio): se registra acá como segundo caso
observado, no como opinión, y refuerza la misma mitigación — preferir JSON crudo de la API de GitHub sobre el
resumen de la página HTML equivalente cuando el dato importa.

### H5 — scikit-learn: última release 1.9.0 (2026-06-02); `train_test_split` sigue con `shuffle=True` por default, sin cambio de comportamiento en splits

Confianza: **alta**.

La ficha de PyPI para la versión 1.9.0 (verificado, cita literal: «Released: Jun 2, 2026») confirma la fecha.
El changelog de la versión 1.9.0 (verificado) no incluye ningún cambio de default en `train_test_split` ni en
el comportamiento general de splitting; los cambios en `model_selection` de esta versión son: `GroupKFold`
pasa a usar sorting estable entre corridas (consistencia, no cambio de resultado esperado),
`StratifiedGroupKFold` ahora lanza `ValueError` si `n_splits` excede el número de grupos únicos (evita folds
degenerados), validación nueva que lanza `ValueError` cuando `sample_weight` es todo ceros, `learning_curve`
enruta mejor `sample_weight` a `partial_fit` con `exploit_incremental_learning=True`, y soporte de callbacks
(`ProgressBar`, `ScoringMonitor`) en `GridSearchCV`/`RandomizedSearchCV`/`HalvingGridSearchCV`/
`HalvingRandomSearchCV`.

Impacto ML: el caso de evaluación `07-split-y-mejora` (pasa desde 2026-08-23) se apoya en que
`train_test_split` barajea por default y que la semilla da reproducibilidad, no validez. Esta corrida confirma
que ese mecanismo sigue vigente en la versión actual de la librería (1.9.0): no hay nada que corregir en la
respuesta ya evaluada de ese caso, ni motivo para revisar el caso por esta vía.
